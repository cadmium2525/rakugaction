## PHASE 2: ラクガキエディタ

### 実装
* `src/drawing/model.ts` — ストローク列 (pen/erase/fill) のデータモデル、上限 (op 400/パーツ, 点 3000/ストローク)、座標は 1/4096 に量子化。パーツ = body/head/armLeft/armRight/legLeft/legRight。左 = 画像の右 (+x)。
* `src/drawing/raster.ts` — **Canvas 非依存**のソフトウェアラスタライザ (384²)。距離ベース AA、消しゴム、閉領域の塗りつぶし (外周に触れる領域は塗らない/線のにじみは塗りの上に重ねる)、ライブ描画と一括再生が一致。エディタ表示と 3D 化の元データが同一。

* `src/drawing/editorState.ts` — パーツ別 Undo/Redo、全消去 (Undo 可)、全リセット、左右コピー (OFF にすると反転コピーが出発点)。
* `src/drawing/defaults.ts` — 空のパーツは既定形状 (カプセル) で補う → 「何も描かなくても成立」。
* `src/character/layout.ts` — 6 パーツのマスクから頭/胴/腕/脚の配置を決定 (重ねて接続する方針)。PHASE 3 の 3D 化も同じ結果を使う。
* `src/ui/editor/*` — 4 ステップ (からだ→あたま→うで→あし)、ガイド、ペン/けす/ぬる/もどす/すすむ/ぜんぶ、12 色、4 太さ、ライブ合成ミニプレビュー、プレビューモーダル。
* `src/ui/titleScreen.ts`, `src/app/app.ts` — タイトル → エディタの画面遷移。ゲームシーンは離れる時に WebGL ごと破棄。

## PHASE 3: 2D→3D 生成 + 誕生演出

### 実装
* `src/character/maskOps.ts` — 距離変換 (Felzenszwalb 厳密 EDT)、穴埋め (外周 8 近傍連結を外とみなす)、4 近傍ラベリング、小片除去 (最大成分は必ず残す)、膨張、内接円半径。
* `src/character/contour.ts` — ピクセル境界追跡 (ピンチ点は右折して成分を分離 = 常に単純な輪郭)、[1 2 1] 平滑化、Douglas-Peucker、自己交差検査。**平滑化/許容誤差を段階的に弱めて再試行 → 最後は凸包**で、どんな絵でも単純多角形を得る。
* `src/character/cleanPart.ts` — シルエット整形 (穴埋め → ゴミ除去 → 最小の太さ補正 + 常時 2px 膨張) とテクスチャ生成 (192²、囲まれた未塗りは紙色、膨らませた縁は近傍色でにじませ)。
* `src/character/partGeometry.ts` — ExtrudeGeometry + ベベル (bevelOffset 負 = シルエットは描いた形のまま) + creased normals + 平面投影 UV。**側面/ベベルは輪郭線の内側の色をサンプル**して、黒い縁取りが側面全体に回らないように。裏面は暗く。三角形予算 3200/パーツ (超えたら輪郭を粗くして作り直し)。
* `src/character/builder.ts` — `buildCharacter(drawing)`: 6 パーツ → 整形 → レイアウト → rig 組み立て (root→body→head/armL/armR/legL/legR、関節がピボット)。前面をそろえた Z 配置 (2D プレビューと同じ重なり)。例外を投げない。
* `src/render/renderHost.ts` — WebGL (canvas) をアプリ全体で 1 つに共有 (ゲーム/誕生など複数ビューが借りる)。GameView は借りる側へ。
* `src/render/showcaseView.ts`, `src/ui/birthScreen.ts` — 誕生演出: 平らなラクガキが浮かぶ → ポンッと立体化 (z スケールがエラスティックに膨らみ回転) + キラキラ → 着地スカッシュ + 砂ぼこり → 「たんじょう！」→ ボタン。タップでスキップ。ターンテーブル待機。
* `src/dev/doodles.ts` — 極端ラクガキ 15 種のフィクスチャ (テストと `?birth=<name>` で共有)。

## PHASE 4: 手続きアニメーション

### 実装
* `src/character/animator.ts` — `CharacterAnimator`: Idle / Walk / Run / Jump / Fall / Land を、リグのピボット回転だけで表現 (手足の伸縮なし)。
  * 歩行周期は速度と脚の長さから決定、振れ角は手足の長さで補正 (長い手足は小さく/短い手足は大きく)、左右逆位相、走りで前傾。
  * Jump: 腕を上げ脚を前後に / Fall: 手足を広げてばたつく / Land: 衝撃に比例したスカッシュ & ストレッチ (Y 潰れ・XZ 膨張) と脚の曲げ。
  * 全チャンネルを指数スムージングで遷移。着地は `landCount` の増加で検出。
  * **地面に埋まらない保証**: 手足の外接箱の 8 隅を毎フレーム root 座標へ変換し、脚の最下点が 0 未満なら体ごと持ち上げる。**長すぎる腕**は構築時に立ち姿で clearance が取れる角度まで外へ開く (rest splay)。
* `PlayerView` をアニメーター駆動に置換 (仮の傾き/スカッシュを廃止)。`ShowcaseView` も待機にアニメーターを使用 (`demoState` でその場 walk/run/jump/fall を再生可)。
* `PlayerController.landCount` 追加。毎フレームの allocation を排除 (pose の再利用)。

## PHASE 5: 能力生成

### 実装
* `src/character/colorClass.ts` — RGB → 赤/黄/緑/青/紫/無彩色 へのソフト分類 (色相環の隣り合うアンカーへ線形配分: 橙=赤+黄, 水色=青+緑, ピンク=赤+紫。黒/白/灰/茶は無彩色)。
* `src/character/measure.ts` — 形状計測 (全高/幅/各パーツの面積・寸法・厚み/重心/接地幅/脚の長さ/左右非対称) と色の使用割合。`measureDrawing()` はジオメトリ無しの軽量版。
* `src/character/statGen.ts` — `computeStats()`:
  1. 形状特徴量 (基準との対数比) → 6 能力 (大きい体: HP/DEF/WEIGHT↑ SPEED/JUMP↓、長い脚: SPEED/JUMP↑、太い腕: POWER/WEIGHT↑、太い脚: JUMP↑、縦長で小さい体: SPEED↑)。キャンバスに上限がある量 (脚/腕の長さ/全高) は「描ける最大」で +0.7 になるよう伸ばして、長い側/短い側の効果を釣り合わせる。
  2. 色 (赤=POWER 青=DEF 緑=SPEED 黄=JUMP) を **最大 +20% の副次補正**として加算。紫の割合は `special`。
  3. **能力値の予算 (対数の平均) を 0 にそろえる** → ある能力を伸ばせば他が必ず下がる (最強形状が構造上作れない)。色補正も予算の内側。
  4. ソフトクランプ (約 45〜222)。traits: size (体の大きさ → 見た目/当たり判定), reach (リーチ), stability (足幅/重心/脚の長さ)。
  5. `describeBuild()`: 重量型/高速型/ジャンプ型/力持ち型/守り型/バランス型/極端型 のラベル。
  * 基準 (REF) = エディタのガイド形状をなぞった `referenceDoodle()` の計測値 → 全能力 100。
* `src/game/params.ts` を再較正: 最高速度 ≈ 4.7〜10 m/s、ジャンプ初速 ≈ 7.4〜14 m/s に収まる指数 (SPEED^0.5, JUMP^0.4)。WEIGHT は加速/摩擦/旋回/風耐性/沈みやすさ/ノックバックに効く。
* `buildCharacter()` が能力解析まで行い、全高 = 1.6m × size。`BuiltCharacter.analysis` を誕生画面の **能力カード** (`src/ui/statCard.ts`: ビルドラベル + 6 本のバー + 「ふつう」目安線 + なまえ入力) に表示。誕生後の「あそぶ」は描いた形から決まった能力で走る。
* `src/character/record.ts` — 保存単位 `CharacterRecord` (PHASE 14 で使用。`STAT_FORMULA_VERSION` で式変更時に再計算)。
* `src/dev/randomDoodle.ts` (plausible/wild の 2 プロファイル)、`src/dev/doodles.ts` に基準ラクガキ/バリエーション/**テストビルド元ラクガキ**を追加。**TEST_BUILDS の能力値は実際のラクガキの計測値と一致**させ (テストで検証)、「現実に作れる範囲」でバランスを検証できるようにした。

## PHASE 8: STAGE 3 水没神殿

### 実装
* **水中の物理** (`player.ts`/`params.ts`/`water.ts`): 水域 (AABB) に入ると泳ぎ状態。**浮力** = (1 − 密度) × 16 (軽い/膨らんだ体は浮き、密度の高い重い体は底へ沈む)。JUMP で浮上 (水面で頭を出して止まる)、ACTION で潜水、水面で JUMP すると水から跳び出して縁に上がれる。**泳ぎ速度は体が小さいほど速い** (SPEED 5.64 / STANDARD 4.34 / HEAVY 2.78 / EXTREME 2.50 m/s)。水位は `level` (振幅/周期/位相) で時間に応じて上下し、時間の純関数 (`surfaceOf`) なので決定的。

## PHASE 10: STAGE 5 巨人の塔

### 実装
* **動く危険物 (sweeper)** (`SweeperDef` / `GameSim.sweepers`): 経路は移動床と同じ (経過時間だけで決まる = 決定的)。床ではなく、触れるとダメージ + ノックバック。ジャンプで飛び越えられる。`sweepersClear(min,max,seconds)` で「今から N 秒間その領域に来ないか」を調べられる。描画は赤いブロック + 黒い縞。`PathBuilder.sweeper()` / `branchAt()` (今いる床の脇から向きを変えた近道を作る)。

## PHASE 11: ユーザーレベル / EXP

### 実装
* **`src/progression/level.ts`** (純関数): レベル上限 20。Lv.n → n+1 に必要な EXP = `round(60 × 1.22^(n-1))`。`levelFromExp` / `expForLevel` で累計 EXP と相互変換。
  * **レベル補正 `applyLevel(stats, level)`**: HP / POWER / DEFENSE / SPEED / JUMP に **全部同じ割合 (+0.75% / Lv)** → 形のバランスは変わらない。さらに **得意な能力 (上位 2 つ。105 超のみ)** にだけ **+0.35% / Lv** を上乗せ → 成長するほど個性がはっきりする (最大と最小の差は広がる)。Lv.20 で全能力 +14.25% 前後・得意な能力 +22% 前後。最大 HP は **Lv.10 と Lv.20 でハート +1**。レベルで能力が下がることはない。
  * **WEIGHT (体の重さ) はレベルで変えない**: 体重が変わると風/水/崩れる床との相性が変わって、成長というより別のキャラになってしまうため (最初は全能力に掛けて、STAGE 2 の本道が 58s → 34s と激変して発覚)。
* **`src/progression/exp.ts`**: ステージクリアの EXP = (40 + 20 × ステージ番号) × (初回 2 倍 / 2 回目以降 35%) + ランクの上乗せ (S +50% / A +25%) + NEW BEST +10。内訳は全て 0 以上。ALL STAGES TIME ATTACK 用の `allStagesExp` (初完走 300 / 以降 60 + ベスト更新 40) も用意 (PHASE 12 で使う)。
* `Profile.exp` / `level` / `progress` / `addExp` (負・NaN は無視、上限の 100 倍で頭打ち)。`statsToParams(stats, traits, extraHearts)`。
* **UI**: 結果画面に「Lv.N [ゲージ] +N EXP」と内訳、レベルアップ時は「LEVEL UP! Lv.a → Lv.b」と増えた内容。ハブに Lv バッジ + 次のレベルまでのゲージ、能力カードに補正で増えた分 (+1 など)。レベルアップ後の「もういちど」は新しい能力で再開。
* ステージを遊ぶ時の能力 = `applyLevel(キャラの能力, プレイヤーレベル)` (App.paramsOf)。

## PHASE 14: セーブ / ロード

### 実装
* **スキーマ** (`src/save/schema.ts`): `SaveData` (schemaVersion / savedAt / gameVersion / profile (キャラクター・選択中・ステージ記録・ALL STAGES ベスト/回数・EXP) / settings (画質))。**バージョンつきマイグレーション** `migrate()` (v0 = 開発中の旧形式 → v1 を実装。`MIGRATIONS[n]` を 1 段ずつ適用)。**このアプリより新しいバージョンのデータは読まない** (`newer`)。
* **検証・修復** `normalizeSave()` (例外を投げない): 能力値は 20〜300 の整数 (不正は 100)・特性は範囲内に・ラクガキは `sanitizeDrawing` を通し、空/壊れたキャラクターは破棄・id の重複/欠落は一意に・名前は整形・選択中が消えたら先頭に・キャラは最大 12 体・ステージ id は `stageN` だけで矛盾 (ベストがあるのに未クリア) は直す・EXP/回数/ベスト/画質の範囲・**能力の計算式 (`formulaVersion`) が古いキャラはラクガキから再計算**。修復した内容は `issues` に残る。
* **保存先** (`src/save/store.ts`): **IndexedDB → localStorage → メモリ** を使える物から選ぶ (`createSaveStore`)。保存するのは **チェックサム付きの包み** (`wrap`/`unwrap`: 途中で切れた/手で書き換えた/ビット化けを検出)。**main + backup の 2 世代**: IndexedDB は「今の main を backup へ → 新しい main」を **1 つのトランザクション**で行う (途中で止まっても壊れない)。localStorage は backup を先に書く (容量不足でも main は書き込み前のまま)。開くのが固まる/例外の環境はタイムアウトで次の保存先へ。
* **`SaveManager`** (`src/save/manager.ts`): `load()` は **main → 壊れていれば (壊れた main は調査用に退避) backup → それも駄目なら最初から**。結果は `empty/ok/migrated/recovered/reset/newer/unreadable`。**`newer`/`unreadable` の時は保存を止める** (新しい版のデータや、一時的に読めなかっただけのデータを空のデータで上書きして消さない)。`schedule()` は 0.4 秒のデバウンスで 1 回にまとめ、書き込みは 1 つずつ順番に (古い保存が新しい保存を追い越さない)。保存失敗 (容量不足など) は例外にせず通知。4,000,000 文字を超えるデータは保存しない。
* **App 連携**: `Profile` の変更メソッド (キャラ追加/選択/削除・クリア記録・EXP・ALL STAGES) が `onChange` を出し、自動保存。ページが隠れる/閉じる時 (`visibilitychange`/`pagehide`) に `flush()` (非同期書き込みなので最善努力。通常はデバウンス 0.4 秒で保存済み)。復旧した/変換した/再計算した時は **すぐ書き直して** 壊れた main を残さない。起動時に状態をトーストで知らせる (復旧しました / 復旧できず最初から / 新しい版のデータ / 読み込めない / このブラウザでは保存できない)。開発用のショートカット起動 (`?doodle=` など) は既定で保存しない (`?save=1` で保存)。
* **UI**: **キャラクター一覧** (選ぶ/ハブへ・削除は 2 回押して確認・12 体まで・いっぱいなら「いらない子を けしてね」)、**せってい** (画質 じどう/ひくい/ふつう/たかい・保存先と状況・最後の保存時刻・保存失敗の表示・セーブデータを全部消す (2 回押して確認))、タイトルは保存があれば「つづきから」。画質の設定は保存され次回から使われる。
* **ハブを横向きスマホ (高さ 420px 以下) で 1 画面に収める**: 実際に 812×375 で確認したところ中身 692px / 表示領域 355px で能力カードとメニューが折りたたみの下に隠れていた (私が追加したボタンで悪化)。→ ステージカードを 1 行に、能力カードをキャラクターの横 (左上) に、メニューを 3 列に。812×375 と 667×375 で **スクロールなし**を確認。

### 問題の発見
6 つの代表ビルドの最速ルート合計: SPEED 191s / JUMP 223s / STANDARD 243s / POWER 257s / HEAVY 306s / EXTREME 332s。**5 ステージ中 4 つで SPEED が勝ち、EXTREME は 1 ステージ以外で最下位** (最大/最小 1.74 倍)。

### 調整 (仕組み)
1. **水底歩行** (`player.ts`): 水底に立っている間は泳がずに歩ける。歩く速さは地上の 45%〜80% で **密度に連続的に比例** (密度 0.9 → 45%、1.2 以上 → 80%)、実際の上限は「泳ぎ」と「歩き」の速い方 → 軽い体は今までどおり泳ぎ、重い体ほど歩く方が速い。最初に固定の密度閾値で作ったが、STANDARD (1.000) は泳ぐのに JUMP (1.029) は歩く、という**崖**ができるため連続式にした。※密度 = weight^0.9 / size^0.6 なので **大きい体は水を押しのけて浮きやすい** (HEAVY は 1.008 でほぼ中性浮力。EXTREME は 1.22 で沈む)。
2. **S3 のポンプ室の待ち方** (ボット/ルート): 水位待ちを足場から離れた所でしていたため、遅い泳ぎ (HEAVY/EXTREME) は 5.4 秒の高水位の窓に間に合わず **丸ごと 1 周期 (18 秒) 損していた** (HEAVY 69s / EXTREME 71s vs 他 48〜52s)。→ 足場の真下 (水底) まで先に行って待つ。ボットは「水面近くまで浮上してから」水上ジャンプするように (深い所での JUMP は浮上の泳ぎになり空振りしていた)。結果 HEAVY 53s / EXTREME 54s。
3. **S2 の横風 12.5 → 14.0 m/s**: 風を押し切れる体重の境目 (体重 ≈ 108〜110 の JUMP/POWER が「押し切れる側」に入っていて、最高速度の差だけで勝っていた) を HEAVY/EXTREME だけが押し切れる側へ。13.5〜14.5 が安定した台地 (15.5 では HEAVY も渡れない) → 中央の 14.0。HEAVY 41.7s / EXTREME 43.4s が JUMP/POWER (58〜59s) より明確に速い。
4. **木箱の抜け道** (`src/stages/crateBypass.ts`, S1 と S4): 通路の途中に木箱の壁 (toughness 0.95) があり、**攻撃力が標準以上 (STANDARD/POWER/HEAVY/EXTREME) は壊して直進**、壊せない SPEED/JUMP は大回り (同じ向きで合流)。遅いビルドほど短縮の効果が大きい (HEAVY S1 72→62s)。S1 の `dash` (SPEED の 6.4m ジャンプ) と共存するようルート組み立てを `RouteSet` に載せ替え (分岐の直前の「台の端の中央」ウェイポイントを本道だけに入れ、近道は台の中を斜めに助走する元の形に)。
5. **S5 の炎の通路** 16m → 22m・ダメージ 1.0: HEAVY (HP 4・DEF 0.89) だけが 4 回浴びても耐える (残り HP 0.44)。HP 3 のビルドは SPEED も含め倒れる。連絡路が長い 4F の外周だけ鉄球を 3 つに (近すぎると渡る位置が次の鉄球の危険範囲に入って被弾する)。

## PHASE 17: STAGE 1 のリッチ化と敵 (試作)

### 敵 (シミュレーション。`src/game/enemies.ts` + `GameSim`)
* 4 種類: **ぷるん** (ゆっくり巡回。ふんづけ/ACTION で倒せる)・**ぴょんた** (ためて跳ねながら進む)・**トゲまる** (上からふむと痛い。ACTION は `攻撃力 >= 0.95` (木箱と同じ基準) のキャラだけが倒せる = POWER の出番)・**おいかけくん** (気づくと追いかける。範囲 `leash` の外へは出ない)。
* 巡回する敵の位置は経過時間だけで決まる (移動床/鉄球と同じ = 決定的)。chaser だけプレイヤーの位置に反応するが、これも入力が同じなら同じ結果。
* 判定は円柱 × 円柱で、優先順位は **ACTION → ふんづけ → 接触ダメージ**。ふんづけは落下中 (vy <= -1) に足が敵の上の方に来た時 (トゲは不可)。倒すとはね返る (ジャンプを押し続けると高い。`PlayerController.bounce`)。攻撃力が足りない ACTION は `guard` (はね返される)。接触は DEFENSE で軽減・ノックバック・無敵 1.1 秒 (他のダメージ源と同じ `hurt()`)。やられて復活すると全員元に戻る。
* ボット: 「前方の、届く範囲 (+ 踏み込みぶん) の倒せる敵に ACTION」(`Bot.fight`)。倒せない敵は経路 (レーン) で避ける設計にした。
* 結果: クリア時の「たおした てき n / 全部」、1 体 EXP +3 (最大 +30) (`stageExp` の `enemiesDefeated`)。
* STAGE 1 に 8 体: ぷるん ×4 (最初の原っぱ ×2・合流の台・スロープ後)、ぴょんた ×2 (丘の下・飛び石のあと)、トゲまる ×1 (木箱の抜け道の通路)、おいかけくん ×1 (ゴール前の広場)。**ボットは全 6 ビルド・全ルートで死亡 0・被弾 0** (敵は ACTION の踏み込みで倒され、タイムは HEAVY の S1 が 61.9→65.4 秒になったほかは変わらない (STANDARD 50.4 / SPEED 49.3 / JUMP 61.4 / POWER 55.8 / EXTREME 67.6)。合計の偏りは調整済みの範囲のまま。`tests/balance/allStages.test.ts` 合格)。

## PHASE 18b: 崖の丘を「外周を回って登る塔」に作り替え

### きっかけ
ユーザーの評価: 「崖の上にある星は、ジャンプと歩行の連打で登り切れてしまう。仕掛けとしては外周を回りながらてっぺんを目指す形のはず」。最初の崖の丘は、最大 43° ほどの滑らかな山 + 土の道 (らせん) で、道を使わず直登できた (私の設計ミス)。

### 経緯 (試して分かったこと)
1. 地形を渦巻きの段々 (道の幅だけ平ら + 周回の間は 5m の崖) にした → 直登を検出するテスト (8 方向 × 6 ビルド、行き止まりで自動ジャンプするボットで 45 秒) が**失敗**。原因: 高さフィールドは 2m 格子なので、5m の崖は 50〜60° 台の斜面にしかならず、ジャンプしながら押し込むと登れてしまう。
2. 崖を 1 セルの段差 (68°) にしても、擁壁 (垂直な箱の壁) を足しても失敗。段差の斜面の「裾」が壁の外側に残り、そこに飛び乗ってから壁を越えられる高さになる (トレースで確認)。
3. **解決**: 崖の丘は地形ではなく、**石のブロック (地面から立つ柱) を螺旋に並べた塔**にした (`stages/stage1.ts` の `cliffTower`)。上面は 0.2m 刻みの階段 = 登り坂、周回の間はブロックの垂直な側面なので、裾が生まれない。頂上は中心の円柱 (旗つき)。地形の `spiralMountain` は削除した。

### 仕様
* 幅 6.4m の螺旋状の段が外側から内側へ 2 周、1 周で +5m (頂上は高さ 10m)。誰も 5m は跳べない (最大のジャンプ 2.69m)。入口 (東側) は外の地面から 0.2m の段。外周をぐるぐる回って登る。落ちても下の周回に戻るだけ。1 周目の外側は地面から最大 5m の壁なので、SPEED/JUMP が 2.5m 以下の所から飛び乗って道を一部省略することはできる (道の途中から入るだけ)。
* 1 周目の道の中央にプルン、2 周目の内側のレーンにトゲマル (外側のレーンを通ればかわせる)。
* ボットの `cliff` ルート (崖の上 + 花畑 + 池 + 風車の丘 + トゲ畑の先): 全 6 ビルドがクリア (STANDARD 78 / SPEED 64 / JUMP 81 / HEAVY 97 / POWER 86 / EXTREME 107 秒)。本道より 15〜20 秒遅い = 崖の星は一番手間のかかる星。
* テスト (`tests/stages/stage1.test.ts`): ① cliff ルートを全ビルドがクリア ② 頂上の星へ、渦巻きの外 26m の 8 方向から真っすぐ向かう (行き止まりでは自動で跳び続ける) 全 6 ビルドが、45 秒で星に届かず、地面に立てた最高が 5.3m 未満 (2 周目の道に立てない)。
* ミニマップは y 軸まわりに回した箱も回した長方形で描く。

### 学び
* 高さフィールド (格子 2m) では垂直な崖は作れない。ジャンプで越えさせたくない垂直の壁・崖は、箱 (ブロック) で作る。直登できないことは「連打するボット」で検証する。

## PHASE 19: 自由スケッチ (四足・多腕…) + ふくらませた立体 (v0.4.0)

### きっかけ (ユーザーの評価)
「自由スケッチ (四足・多腕。絵の向きはパーツごとに正面/横向きを選べる方式) をやろう。もうちょっと出来上がるキャラのフォルムをどうにかならないか。平面に描いたパーツが奥に伸びただけの立体はイマイチ」。設計は DESIGN 5.7。

### 実装
* **形**: 輪郭の押し出しをやめ、マスクを**ふくらませる** (ポアソン方程式で内側ほど盛り上げ、z = K√h)。表裏を共有した輪郭でつなぐ・法線は滑らか・平面投影のテクスチャ。`tests/character/inflate.test.ts` が円/細長/L 字/ドーナツ/飛び地の水密性・向き・空マスクを検査。
* **縁**: 絵の黒い縁取りを検出して内側の色に置き換え、縁を暗くするシェーダーで立体の輪郭に (横から見た時に黒い帯にならない)。
* **データ**: v2 (パーツのリスト)・v1 からの変換・保存スキーマ 1→2 の migration・能力式バージョン 2。
* **配置/アニメーション/能力**: `layout.ts` `prepare.ts` `animator.ts` `statGen.ts` をパーツのリスト前提に。人型は旧実装と同じ数値 (既存の REF/バランステストがそのまま通る)。
* **エディタ**: パーツチップ・ひな形・パーツ設定・つなぐ位置 (ドラッグ)・ガイド・合成プレビュー。
* **誕生画面**: 横向きの胴体は、絵の面がカメラに向く (前が画面の右) ように 90° 回して見せる。「平らなラクガキ」の演出は左右 (x) 軸をつぶす。
* **開発用**: `?doodle=quadruped|asura|bird|insect|chimera|allDefaults(quadruped)…` (`dev/doodles.ts` の `creatureDoodles`)、`randomCreature` (ランダムな自由スケッチ)。使われなくなった `character/contour.ts` とそのテストを削除。

### 検証
* lint / tsc / vitest (443 件) / build すべて通過。
* 追加テスト: 生きもの 7 種 (四足・阿修羅・鳥・虫・混成…) の 3D 化・階層・脚の本数と配置・足が地面に着く・三角形数 (`tests/character/creatures.test.ts`)、歩行の位相 (2 本/4 本/6 本)、全アニメーション状態で姿勢が壊れない、ランダムな自由スケッチ 14 体の 3D 化と動き、ランダム 180 体の能力分布 (全能力 40〜230・予算が基準から大きく離れない)、サニタイズ往復、v1→v2 の読み込み。
* アプリ内ブラウザ (844×390): 新エディタの表示、パーツ追加ダイアログ、つなぐ位置のドラッグ、プレビュー → 生成 → 誕生画面 (四足)、STAGE 1 を四足で走らせて確認。
* 能力のバランス: 腕が無い生きものが POWER の下限 (約 50) に張り付き、予算が少し膨らむ (最大 1.045 倍) ことを新しい検証で発見 → 腕が無い時の特徴量を −0.55 に。膨らみは最大 1.03 倍程度に減った (人型の検証は 1.02 以下のまま)。

### 後追い: 顔が背中側にも出る (後ろ歩きに見える) 問題 (ユーザーの指摘)
旧実装から、顔を描くと**背中側にも同じ絵が出て**、後ろから追うカメラには「こちらを向いたまま後ろ歩き」に見えていた (ふくらませた立体でも背面は前面の鏡像で、直っていなかった)。正面の絵のパーツは、背中側のテクスチャから小さな描き込みを消す (`backTexture.ts`、DESIGN 5.7)。目・口・ボタンのある顔つきの人型 (`facedDoodle`、`?doodle=faced`) で、前は顔あり・後ろは無地になることを実画面で確認。テスト: `tests/character/backTexture.test.ts` (領域の分け方・最大領域は残る・背面にだけ顔が無い・材質グループが三角形を過不足なく覆う・前面は +z 側/背面は −z 側・2 つ目の材質も破棄される・横向きは 1 材質)。ビルドの記録は `meshes` (メッシュ数) と `drawCalls` (描画呼び出し) を分けた。

### 残り / 未検証
* **実機 (スマホ) でのエディタの操作感は未確認** (ボタンの大きさ・「つなぐ位置」のドラッグ・パーツが増えた時の画面の狭さ)。アプリ内ブラウザの 844×390 で見た範囲のみ。
* **本当に人が描いた四足/多腕の見栄え**は未確認 (テスト用の絵は自分で用意した単純な図形)。パーツの根元がうまくつながらない絵・横向きと正面が混在した時の見え方は人の評価待ち。
* 四足の初回 3D 化は約 0.4 秒 (デスクトップ)・約 1.2 万三角形。実機の生成時間・メモリは未確認。
* 自由スケッチのキャラが全ステージで遊べるかは、ボットでは人型のビルドしか攻略していない。四足・多腕でのステージ攻略 (当たり判定は従来と同じカプセル) は人の評価待ち。
* STAGE 2〜5 のフィールド化・ボス戦はまだ。

* **頭を紙の 45% に小さく描いた顔: 目の輪郭が白目・黒目に滲んでぼやける**。原因は、3D 用の絵が紙全体で 192×192 (ラスタ 384 の 2×2 平均) なので、小さく描いた細部の解像度が足りない (目が 8 テクセル)。v0.7.0 の「大きさ」で紙いっぱいに描いて小さく貼れば避けられるが、気づきにくい。**直ってはいなかった (部分的な回避のみ)**。

### 提案への評価と実装
* **採用**。理由: (1) 滲みの原因 (解像度) を、貼る絵に自分の紙の解像度をそのまま使うことで根本から避けられる (2) 頭の絵に顔があると、輪郭の帯の除去・背中側の簡略化 (顔が背中に出ないようにする `backTexture`)・暗い領域の判定といった「顔を消す・直す」処理が絶えず当たっていた。もようは形を持たないので、これらを通らず、変なバグが起きにくい (3) 形・能力に関係しないので既存のデータ・テストに影響しない。
* 貼り方は、最初は表面にレイを当てた格子のパッチ (24 → 48 分割) にしたが、**貼り先と陰の境目がずれて目の上にぎざぎざが出た**ため、貼り先の三角形をそのまま写す方式に変えた (陰影が完全に一致)。詳細は docs/DESIGN.md 5.7。
* 途中で見つけて直した不具合 (別件): プレビューの 3D ↔ 2D を切り替えて戻すと、WebGL を捨てた canvas を再利用して表示が壊れた → 閉じるたびに canvas を作り直す。

### テスト
`tests/character/decal.test.ts` (11): 保存データ・エディタの既定・形と能力が変わらない・色の計測にだけ入る・空のもようは貼らない・頭のメッシュの子で表面の上 (有限・範囲内・前の面)・ペア (対称な 2 面 / 中心なら 1 面)・頭が無ければ胴体 / onBody・シルエットの外は貼らない・四足は反対側の面・貼る絵 (にじみ・縁の透明)・頭のジオメトリが変わらない。ブラウザで、追加 → 描く → 貼る位置 (実寸の重ね表示) → 左右にも貼る → 3D プレビューを確認。

### 未検証 / 残り
* 実機での見え方・負荷 (貼る絵 1 枚 = 384×384 RGBA 約 0.6MB + ミップ。4 つまで)。
* 頭に直接描いた小さな顔の滲みそのものは、そのまま (もようを使うか、「大きさ」で紙いっぱいに描くのが対策)。紙の描いた範囲に絵の解像度を合わせる (テクスチャの切り出し) 案は、UV・輪郭の除去・背中側・alt の座標がすべて関わるため見送った。
* もようは回転・変形・複数の貼り先の選択 (腕や脚に貼る) は無い (頭か胴体のみ)。斜めの面では絵が引き伸ばされる (平面投影)。
* ひな形には「顔」のもようの枠を入れていない (「＋足す」から足す。頭のヒントで案内)。

### 測り方 (主観を減らすため、同じ物差しで前回と今回を測った)
`scratch/sketch/metric.py` (git 管理外): 見本から被写体を色で切り出し (`seg.py`)、再現の輪郭も同じように切り出して、**大きさ・位置を自動で合わせてから** 輪郭の重なり (IoU = 共通部分 ÷ 合併) と、重なった部分での粗い色の分類 (赤・金・白・灰・青・暗・その他) の一致率を測る。見本が切れている部分 (翼・しっぽ) は、見本の枠で切る。切り出しは目視で確認した (ドラゴンは金の膜・腹・とげ、オオカミは青・白・灰・角を含める)。

* **後ろ向きのドラゴンは悪化 (0.629 → 0.522)**: 翼の絵が正面 (見本 1) の形で、見本 3 の翼 (肩で高く、先が大きく垂れる) と違う。**翼を前と後ろで別の形にはできない** (1 枚の翼の絵)。前の版は偶然、後ろ姿で近かった。見本は姿勢が方向で大きく変わる (翼が傾く・首を前に出す・しゃがむ) ので、固定の姿勢の 1 体では全方向を合わせきれない。
* 色の一致が下がった箇所 (ドラゴンの左向き 0.870 → 0.766): 前回の翼は赤一色で、横から見た見本の赤い翼と色が近かった。今回は翼の表を金にしたため、横から見える翼に金が出て、見本 (横から見える翼は赤い裏面) と合わなくなった。

### テスト中に見つけて足したもの
* **前後のずれ `PartSlot.forward`** (詳細は docs/DESIGN.md 5.7): 見本 2 の首を前に出した姿勢は、「もう一つの向きの絵」のずらしがパーツの紙の半分までしか届かず、頭を極端に大きな紙に描くしかなかった → パーツごとに前後へずらせるように。

* 翼の傾き・首の向きのような「姿勢そのもの」は、パーツの向きを回す機能が無いので、近似 (厚みの形・ずれ) のみ。

## PHASE 23: スケッチをもう一段階 (パーツの傾き + お手本を敷く) (v0.10.0)

### きっかけ (ユーザー)
再テストの結果を受けた次の作業の選択で、「スケッチをもう一段階」(候補: パーツの傾き = 回転 / 見本の写真を紙の下に敷いてなぞる機能)。**両方**実装した。

### パーツの傾き (`PartSlot.tilt`、詳細は docs/DESIGN.md 5.7)
* ひねり (上から見て回す)・おじぎ (横から見て倒す)・かたむき (正面から見て倒す)。関節を中心に、メッシュにだけかける (ピボットは回さない = アニメーションと衝突しない)。ペアは左右対称。頭の子 (角) は位置と向きがついていく。
* ドラゴンの翼で試した (`dragon3.mjs`、変種 `wy=ひねり,wp=おじぎ,wr=かたむき`):
  | 翼の傾き | 平均 IoU | 内容 |
  |---|---|---|
  | なし | 0.623 | 基準 |
  | ひねり 25° | 0.553 | 悪化 (正面の見本どおりの形で描いてあるので、ひねると正面の広がりが縮む) |
  | ひねり 45° | 0.504 | さらに悪化 |
  | おじぎ −30° | **0.631** | 後ろ向き 0.522 → 0.574 (翼が後ろへ傾いた見た目)。正面・左向きはほぼ同じ |
  * **結論**: 傾きは姿勢を作れるが、**絵を正面の見本に合わせて描いてあると、傾けるほど正面は離れる**。姿勢をつける時は、傾けた後の見た目に合わせて絵の大きさ・形を直す必要がある (翼なら、ひねる分だけ大きく描く)。IoU の改善は小さい (+0.008)。後ろ向きだけ良くなるのは、見本 3 の翼が後ろへ傾いて見えるため。

### お手本を敷く (`refImage.ts`)
