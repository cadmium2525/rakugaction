# ランキングに 3D の姿を載せる + 管理者による審査 (設計案)

**状態: 設計案 (未実装)。** 今のランキング (`docs/RANKING.md`) は、名前・タイム・能力値だけを載せている。
ここでは「上位のキャラクターの 3D の姿を見られるようにする」ことと、「不適切な絵・名前を載せない」ことを両立させる設計をまとめる。
実装は、この案の「未決定」が決まってから。

## 1. 決まったこと (ユーザーとの合意)

| 項目 | 決定 |
|---|---|
| 不適切な絵の判定 | **コードによる自動判定はしない** (形の規則は誤判定が多く簡単に抜けられる・ブラウザ側の判定は書き換えられる)。**管理者が目で見て決める** |
| 公開の時期 | **承認してから出す**。タイムと順位は登録した瞬間に載る。姿 (3D) と名前は、承認されるまで「審査中」 |
| 審査の範囲 | **上位だけ** (既定は TOP 20。順位の高い順に審査)。それより下は「審査中」のまま |
| 管理者の道具 | **ゲームとは別のアプリ (管理者アプリ)**。今後、ランキング以外の管理機能も足せる作りにする |

「載せてから消す」にしない理由: 登録は匿名の ID で行うので、消された人はブラウザのデータを消すだけで新しい ID になり、同じ絵を載せ直せる。
承認するまで出さなければ、問題のある絵が人目に触れる時間がなく、載せ直しも意味がない。

## 2. 見え方

| 記録の状態 | 一覧での名前 | 姿 | 説明 |
|---|---|---|---|
| **承認** (`approved`) | 付けた名前 | 3D (押すと回して見られる) | 管理者が確認した |
| **審査中** (`pending`) | 体型タイプ名 (「高速型」など) | シルエット | 登録した直後・絵か名前を変えた直後・TOP 20 より下 |
| **非表示** (`hidden`) | 体型タイプ名 | シルエット | 管理者が掲載できないと判断した。タイムと順位は残る |
| (削除) | — | — | 記録そのものを消す。あわせて、その匿名 ID の再登録を禁止できる |

* **本人には、自分の姿と名前がいつも見える** (自分の端末にあるデータで描く)。状態も出す:「審査中です」「この絵または名前は掲載できません」。
* タイムと順位は状態に関係なく載る (ランキングとしての即時性は変わらない)。
* 登録する時に注意文を出す:「絵と名前はランキングで公開されます。不適切なものは掲載されません」。

## 3. データ

Firestore の 1 件 (`ranking/{uid}`) に、次を足す。

| 追加する値 | 内容 | 書ける人 |
|---|---|---|
| `look` | ラクガキの絵 (ランキング用に小さく詰めた文字列) | 本人 |
| `status` | `pending` / `approved` / `hidden` | **管理者だけ** (本人が書けるのは `pending` だけ) |
| `reviewedAt` | 審査した時刻 | 管理者だけ |

別に 2 つの集まりを持つ。

| 集まり | 内容 | 書ける人 |
|---|---|---|
| `admins/{uid}` | 管理者の一覧 (この ID は管理者、という印) | だれも書けない (Firebase の管理画面で手で作る) |
| `banned/{uid}` | 再登録を禁止した匿名 ID | 管理者だけ |

### ルール (Firebase のセキュリティルールで守る。ブラウザ側のコードは信用しない)
* 本人が**新しく登録**する時: `status` は `pending` でなければ拒否。
* 本人が**更新**する時:
  * 絵 (`look`) と名前が前と同じなら、`status` は前のまま (承認済みのキャラでタイムだけ縮めても、承認は続く)。
  * 絵か名前が変わったら、`status` は `pending` でなければ拒否 (審査し直し)。
  * 更新できるのは、タイムが縮んだ時か、同じタイムで絵・名前を直した時。
* `banned/{uid}` がある ID は、登録も更新も拒否。
* **管理者** (`admins/{uid}` がある ID) は、`status` と `reviewedAt` だけを書き換えられる・記録を削除できる・`banned` を書ける。タイムや絵は書き換えられない。
* 管理者の ID は秘密ではない (ID を知っていても、そのアカウントでログインできなければ何もできない)。**管理者の鍵・パスワード・サービスアカウントの鍵は、リポジトリにもアプリにも置かない** (今と同じ方針)。

### 絵のデータの大きさ
* 今の保存形式 (座標を小数の文字で持つ) は大きい: 線の多い絵 (約 14,000 点) で約 520KB。Firestore の 1 件の上限は約 1MB。
* ランキング用には、座標を整数 (0〜4095) にして差分で詰める → 同じ絵で数十 KB の見込み。上限 (案: 200KB) を超える絵は、線の点を間引いて収める。それでも収まらなければ、姿なし (シルエット) で登録する。
* 一覧 (TOP 100) を読む時は絵を読まない (軽い値だけ)。姿は、選んだ記録の分だけ読む。
* 他人の絵は信用しない: 読み込んだら、手元の絵と同じ検査 (`sanitizeDrawing`) を通し、立体化に失敗したらシルエットにする。

## 4. 管理者アプリ

### できること (最初の版)
* 管理者としてログインする。
* **審査待ちの一覧**: TOP 20 に入っている `pending` を、順位の高い順に並べる。
* **確認**: 3D の姿を回して見る (ゲームと同じ立体化のコードを使う)・名前・タイム・各ステージのタイム・能力値・登録した時刻。
* **決める**:「承認」「非表示」「記録を削除」「記録を削除して、再登録を禁止」。
* **全部の記録の一覧**: 状態で絞る・あとから状態を変え直す (承認 → 非表示 など)・不自然なタイムの記録を消す。

### 作り (案)
* ゲームと同じリポジトリの中の、**別のアプリ** (`admin/` フォルダ。別の入口・別のビルド)。ゲームの配布物には含めない。
  * 同じリポジトリに置く理由: 立体化・絵の検査・ランキングの値の検査を、ゲームと同じコードで行う (版がずれない・テストを共有できる)。
* 管理機能を足しやすいように、「ログイン」「管理者かどうかの確認」「機能ごとの画面」を分けておく (ランキングの審査は、最初の 1 機能)。
* 管理者アプリの URL が知られても、操作は Firebase のルールが拒否する (管理者のログインが要る)。
* 費用: Firebase の無料プランの範囲 (有料の機能は使わない)。

## 5. ユーザーにしてもらう準備 (実装のあと)
1. Firebase のプロジェクトを作る (今の `docs/RANKING.md` の手順)。
2. 管理者のログイン方法を有効にする (下の「未決定 1」)。
3. 管理者アプリに 1 度ログインして、自分の ID を確認 → Firebase の管理画面で `admins/{その ID}` を作る。
4. 新しいルールを公開する。

## 6. 未決定 (これを決めてから実装する)
1. **管理者のログイン方法**: Google アカウント (パスワードを増やさない。おすすめ) / メールとパスワード。
2. **管理者アプリの置き場所**: (a) ゲームと同じサイトの別の URL で公開する (スマホからも審査できる。おすすめ) / (b) 公開せず、パソコンの手元でだけ動かす / (c) 別のリポジトリ・別のサイトにする。
3. **審査する範囲の数**: TOP 20 でよいか (管理者アプリで変えられるようにする)。
4. **一般のユーザーからの通報** (「この記録は不適切」ボタン): 最初の版に入れるか。承認制なので、無くても不適切な絵は出ない。入れるなら、承認の見落としを拾う用。

## 7. この案でも残ること
* 審査の基準は管理者の判断 (アプリは判断しない)。
* 承認までの間、上位の姿は「審査中」になる (審査の速さ = 管理者がアプリを開く頻度)。
* タイムの不正は、今と同じく「明らかな異常値の排除」まで (`docs/RANKING.md`)。管理者アプリで、不自然な記録を手で消せるようになる。
* 本物の Firebase での動作 (ルール・ログイン) は、プロジェクトを作ってから確認する。
