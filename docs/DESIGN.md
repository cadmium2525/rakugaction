# RAKUGACTION 設計書 (PHASE 0)

ラクガキから生まれた自分だけのキャラクターで遊ぶ 3D アクションゲーム。
静的ホスティング(GitHub Pages)のみで動き、描画 → 3D 化 → 物理 → 保存まで全てブラウザ内で完結する。

## 2. 採用アーキテクチャ

### 技術スタック
| 技術 | 採用理由 | モバイル影響 / Pages 適合 |
|---|---|---|
| Vite 8 + TypeScript 6 | ビルド/HMR/型安全。フレームワークではなくビルドツール | 出力は静的ファイルのみ。`base: './'` でサブパス配信 OK |
| Three.js | 3D 描画 (必須) | tree-shaking 済み ~ 600KB (gzip 150KB 程度) |
| Rapier (`@dimforge/rapier3d-compat`) | 物理 (必須)。WASM を base64 内蔵するので追加ファイル不要・CORS 不要 | ~ 2MB (gzip 600KB)。動的 import で初回描画を邪魔しない。Kinematic Character Controller が壁/坂/段差に強い |
| Vitest | ロジック/物理ヘッドレステスト | 開発時のみ |
| ESLint (typescript-eslint) | lint | 開発時のみ |
| fake-indexeddb | IndexedDB のテスト | 開発時のみ |

UI フレームワーク (React 等) は使わない。DOM + CSS + Canvas 2D の素朴な構成。

### 設計原則
1. **シミュレーションと描画の分離** — `GameSim` (Rapier + プレイヤー制御 + ギミック) は DOM/WebGL に非依存。Node 上でヘッドレス実行でき、ボット攻略/バランス計測/回帰テストに使う。
2. **ラクガキは「ベクターのストローク列」で保持** — Undo/Redo・保存・左右反転・再生成が容易。ラスタライズは自前ソフトウェア実装 (Canvas 非依存) なので Node でテスト可能。
3. **ステージは宣言的データ (StageDef)** — 衝突ジオメトリと見た目を同じ定義から生成。ボット用ルートヒントも同梱。
4. **能力 → 挙動の写像は純関数** — `computeStats()` / `statsToParams()` / `applyLevel()` をユニットテスト。
5. **保存・ランキングは抽象化** — IndexedDB → localStorage → メモリの順にフォールバック。ランキングは `RankingBackend` インターフェース。
6. **ゲーム時間は単調増加時計** — `performance.now()`。操作不能時間 (ロード/演出/ポーズ/バックグラウンド) は除外。

### 座標・単位
メートル、Y-up、固定 60Hz 物理 (1/60 s)、描画は補間。標準キャラの高さ ≒ 1.6m、重力 -24 m/s²。

## 5.5 敵と見た目の作り込み (PHASE 17: STAGE 1 で試作)

* **敵** (`src/game/enemies.ts` + `GameSim`): 4 種類 (blob / hopper / spiky / chaser)。巡回する敵は位置が経過時間の関数 (移動床と同じ = 決定的)、chaser だけプレイヤーの位置で動く。判定は円柱 × 円柱。優先順位は ACTION → ふんづけ → 接触ダメージ。ACTION は `attackPower >= toughness` で倒す (木箱と同じ仕組み)。ふんづけは落下中 (vy <= -1) に足が敵の上の方に来た時 (トゲの敵は不可)。復活 (`respawn`) では、チェックポイントを通った時点で倒していた敵 (`committed`) は戻らず、それ以外は元に戻る。チェックポイントで HP 全回復 (`heal` イベント)。ノックバック (`knockAway`) は足場の縁までの距離を測って弱める。ゴール後は敵・罠の判定を止める。ボットは「前方で届く範囲の、倒せる敵に ACTION」で対応する。
* **見た目** (すべてコードだけ。Blender や外部素材は使わない): ① 表面の模様 (`surfaceMaterial.ts`: ワールド座標の手続き的な模様をトゥーン材質に注入。草・石・木・レンガなど。画質 LOW では無効) ② 小道具の道具箱 (`stages/decorKit.ts`) と、コースの形に合わせて置く `stages/meadow.ts` (縁の草・花・柵・浮島・雲海・丘) ③ 看板 (`signView.ts`) ④ 空気感 (`ambientView.ts`: 花粉・花びら・ちょうちょ) ⑤ 太陽 (`theme.skySun`: 見下ろし気味のカメラの視界に入るよう、光の向きとは別に地平線近くへ置く。深度テストあり)。敵はパーツを 1 体ごとに結合して軽くしている (目・足・影は別メッシュ)。看板は文字面が走りながらでは読めないので、**近づくと画面上部に説明カード (`Hud.hint`) を出す**のが本体 (`SignDef.hint`。`{move}/{jump}/{action}` は端末の操作名に置き換わる = `src/input/labels.ts`)。表面の模様のシェーダーは、画質「ひくい」では別プログラム (模様なし) になり、遠くでは薄れ、動く床の上ではその床の座標で描く。

## 5.6 フィールド型ステージ (PHASE 18: STAGE 1 で試作)

ユーザーの評価 (「ほぼ一本道ではなく、マリオ 64 以降のように広いフィールドを駆け回り、必要なアイテムを集めたりボスを倒したりしてクリアしたい。タイムアタックで攻略を試行錯誤できる自由度が欲しい」) を受けて、STAGE 1 を直線コースから作り替えた。

* **地形** (`stages/terrain.ts` / `terrainBuilder.ts`): 高さフィールド (`TerrainDef`: 頂点の高さ + 地面の種類)。当たり判定は Rapier の `heightfield`、見た目 (`render/terrainMesh.ts`)・敵の足元・小道具の置き場所は**同じ高さデータ・同じ三角形の割り方** (セル内の対角線は (ix+1, iz)–(ix, iz+1)。実験で確認し、`tests/physics/terrain.test.ts` が 400 点で Rapier のレイキャストと 2cm 以内で一致することを保証) から求める。配列は `idx = ix * (nz+1) + iz` (Rapier と同じ並び)。`TerrainBuilder` は丘・台地・くぼみ・道 (高さを均して土の色に)・島の縁 (崖)・ノイズ・色塗りの道具で、乱数を使わず座標だけで決まる。箱・動く床・水・風・敵などは地形と混在できる。
* **クリア条件** (`ObjectiveDef` + `PickupDef`): `collect` = 星を required 個集めるとゴールが開く (総数は pickups の数。全部集めなくてよい)。`GameSim` が取得 (`pickup` イベント)・ゴールの開閉 (`goalOpen`、閉じている間にゴールに触れると `goalLocked`)・取った星の保持 (やられても戻らない) を持つ。条件のないステージ (S2〜S5) は従来どおりゴールに着けばクリア。ボスを倒す形式は未実装。
* **敵の足元**: `EnemyDef.onTerrain` の敵は、毎ステップ地形の高さに沿う (跳ねる敵は地面 + 跳躍)。
* **描画**: 静的な物 (地形・箱・装飾) は空間 (xz) の区画ごとに結合したメッシュ (`stageMesh.buildStaticStageChunks` / `terrainMesh.buildTerrainChunks`) にして、**区画ごとに視錐台カリング + 距離カリング** (霧の距離 × 画質の見える距離)。装飾の `extra` は画質「低」で描かず、`far` (雲海・遠い丘・空の雲) は 1 メッシュにまとめて常に描く。星 (`pickupView.ts`) は星・縁・光の柱の InstancedMesh 3 つ。ゴールは条件を満たすまで灰色 / 開くと金色に脈打つ。地面の模様は草の色の所だけに葉と花を描く (土の道・砂・岩にはつぶつぶ)。
* **ミニマップ** (`ui/minimap.ts`): 地形を 1 枚の絵にしておき、毎フレームはカメラの向きが上になるよう回して貼る。星・ゴール・チェックポイントを印で出し、窓の外の物は縁に寄せる。地形のあるステージだけ表示。
* **ボットのルート**: ウェイポイント列のまま。STAGE 1 は `main` (誰でも: 5 つの星) / `power` (木箱の遺跡: 攻撃力 ≥ 0.95) / `jump` (浮島の階段: SPEED/JUMP) の 3 本。ビルドごとに通れた中で最速のルートを採用する (バランス計測)。
* **垂直な崖は箱で作る**: 格子 (2m) の高さフィールドでは崖が 50〜68° の斜面になり、ジャンプしながら押し込むと登れてしまう。登らせたくない崖 (崖の丘の塔など) は、地面から立つ箱 (ブロック) で作る (`stage1.ts` の `cliffTower`)。`tests/stages/stage1.test.ts` が、行き止まりで自動ジャンプし続けるボットで直登できないことを検証する。
* **作り込みの原則** (`stages/fieldKit.ts`): 置く場所を (x, z) で指定すると高さは地形から決まる (坂の上に浮かない)。`tests/stages/validate.ts` が、全ステージ共通で、危険物・動く危険物・敵・星の足元に床があることを検査する。

## 5.7 自由なキャラクター (PHASE 19: 自由スケッチ + ふくらませた立体)

ユーザーの評価 (「人型しか作れない。どのパーツを描くか選んで、足が 4 本の動物や腕が 4 本の阿修羅も作れるようにしたい」「平面に描いたパーツが奥に伸びただけの立体はイマイチ」) を受けて、キャラクターの作りを 2 つ変えた。

* **データ (`drawing/model.ts`): パーツのリスト**。`DrawingData { v: 2, parts: PartSlot[] }` (先頭は必ず胴体)。`PartSlot = { id, kind, view, side, pair, flip, mount, ops }`。
  * `kind`: body / head / arm / leg / tail / wing / ornament (角・耳)。上限は種類ごとのスロット数 (腕 4・脚 4・飾り 3・他 1) と全体 12。腕/脚のスロットを複数持てば (ペアなら 1 スロットで 2 本) 4 本・6 本・多足になる。
  * `view`: 絵の向き (`front` 正面 / `side` 横向き)。**パーツごとに選べる**。胴体が横向きなら四足の動物の形 (絵の右が前)、正面なら人型。
  * `pair`: 左右 (または奥手前) のペア。1 枚の絵を鏡像にして 2 本にする (描くのは 1 回)。`side` (L/R/C) は単体のとき。`flip`: 絵を左右反転して使う。
  * `mount`: つなぐ位置 (親パーツの絵の上の (u, v))。`null` なら自動 (種類・向きごとに根元の位置を決める)。エディタの「つなぐ位置」で手動指定できる。
  * v1 (固定 6 パーツ) の保存データは `upgradeLegacy` で変換 (左右コピー ON → ペア、OFF → 左右の単体)。`sanitizeDrawing` が v1/v2 を受け、不変条件 (胴体が先頭・id が一意・上限) を守る。保存スキーマは 1→2 に migration (`save/schema.ts`)、`STAT_FORMULA_VERSION` を 2 に (能力は読み込み時に再計算)。
* **配置 (`character/layout.ts`)**: `computeLayout` が全パーツの置き場所を決める。親 (胴体/頭) の絵の中の根元 (帯の中の最も内側の点) と、パーツ自身の根元を重ねる。人型の自動配置は旧実装と**数値まで同じ** (能力値の一致をテストで保証)。横向きの胴体では、絵の水平方向が前後 (z) になり、ペアは奥/手前 (x = ±) に振り分ける。正面の胴体に複数組の脚/腕を付けると奥行きにずらして並べる。
* **ふくらませる (`character/partGeometry.ts`)**: 輪郭を押し出すのではなく、マスクを**ふくらませて丸い塊**にする。パーツの内側の「中心からの距離」が高さになるよう、ポアソン方程式 ∇²h = −2 (境界で h = 0) を解いて h を求め、z = K√h (K = 1.15 × 種類ごとの係数。翼は薄く 0.45) の面にする。面は表裏を共有した輪郭でつなぐ (隙間なし)、法線は滑らか、テクスチャは絵の平面投影 (見えるのは描いた絵そのもの)。細い腕は細い円柱状に、大きい胴は大きな丸みになる。三角形は 1 パーツ約 1 万以下に抑える (格子の数に上限)。
* **輪郭線**: 絵の黒い縁取りは、色の領域として検出して縁の帯を内側の色で置き換え (`cleanPart.stripOutline`)、代わりに**視線に対して縁の側になるほど暗くなる** (フレネル風) シェーダー (`render/toon.ts` の `characterMaterial`) で表現する。立体の縁が黒く見えるが、絵に太い線を引くとその厚みが膨らんで黒い帯になる問題を避けている。
* **アニメーション**: 脚・腕・しっぽ・翼・飾り・頭をパーツごとに駆動する。歩行は脚を組に分けて交互に動かす (2 本 = 左右交互、4 本 = 対角のペア (トロット)、6 本 = 三脚歩行)。腕が 3 組以上のときは余った組が広がって揺れる。翼ははばたき、しっぽは振る。
* **能力**: 特徴量に「腕/脚の本数」「翼」「しっぽ」「飾り」が加わった。腕が多いほど POWER、脚が多いほど SPEED/安定、翼は JUMP を助け WEIGHT を下げ、飾りは DEFENSE、しっぽは安定。腕が無い生きものは、腕の太さ/面積を最低値ではなく −0.55 (頭突き・体当たりで戦える程度) として POWER に張り付かないようにした。予算の正規化は変わらない。
* **エディタ (`ui/editor/`)**: 上部のパーツチップ (胴体・頭・腕…・＋足す)。新規時は「ひな形」(人型/四足/阿修羅/鳥/虫/ゆるキャラ/胴体だけ) を選ぶ。右パネルでパーツごとの正面/横向き・ペア・向きの反転・つなぐ位置・削除。キャンバスの薄いガイドと説明文はパーツの種類と向きで変わる。「プレビュー」は 3D 化と同じ `computeLayout` の結果で描いた 2D 合成。

## 6. ランキング方針 (PHASE 13 で詳細化)

* バックエンド: Firebase Firestore (Spark 無料枠) + 匿名認証。**REST 直叩き**で SDK を同梱しない。API キーは公開前提の識別子で秘密ではない。管理者権限/秘密鍵はクライアントに置かない。
* 1 ユーザー 1 ドキュメント (uid)。ルールで「ベストの更新のみ」「値域」「スプリット合計 = 総タイム」「最小可能タイム」を検証。
* 記録: timeMs / splits[5] / level / characterSummary / stats / paramsHash / gameVersion / flags / 実時間と シム時間の差。後から検証ロジックを追加できるよう `schemaVersion` を持つ。
* 完全な不正防止は目標外。異常値検出とフラグ化まで。
* 未設定/オフライン時はランキング機能のみ「利用不可」表示、ゲーム本体は影響を受けない。
