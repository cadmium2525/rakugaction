# RAKUGACTION 設計書 (PHASE 0)

ラクガキから生まれた自分だけのキャラクターで遊ぶ 3D アクションゲーム。
静的ホスティング(GitHub Pages)のみで動き、描画 → 3D 化 → 物理 → 保存まで全てブラウザ内で完結する。

## 1. 現状分析

|---|---|
| ディレクトリ | 完全に空 (グリーンフィールド) |

## 2. 採用アーキテクチャ

### 技術スタック
| 技術 | 採用理由 | モバイル影響 / Pages 適合 |
|---|---|---|
| Vite 8 + TypeScript 6 | ビルド/HMR/型安全。フレームワークではなくビルドツール | 出力は静的ファイルのみ。`base: './'` でサブパス配信 OK |
| Three.js | 3D 描画 (必須) | tree-shaking 済み ~ 600KB (gzip 150KB 程度) |
| Rapier (`@dimforge/rapier3d-compat`) | 物理 (必須)。WASM を base64 内蔵するので追加ファイル不要・CORS 不要 | ~ 2MB (gzip 600KB)。動的 import で初回描画を邪魔しない。Kinematic Character Controller が壁/坂/段差に強い |
| Vitest | ロジック/物理ヘッドレステスト | 開発時のみ |
| ESLint (typescript-eslint) | lint | 開発時のみ |
| fake-indexeddb | IndexedDB のテスト | 開発時のみ |

UI フレームワーク (React 等) は使わない。DOM + CSS + Canvas 2D の素朴な構成。

### 設計原則
1. **シミュレーションと描画の分離** — `GameSim` (Rapier + プレイヤー制御 + ギミック) は DOM/WebGL に非依存。Node 上でヘッドレス実行でき、ボット攻略/バランス計測/回帰テストに使う。
2. **ラクガキは「ベクターのストローク列」で保持** — Undo/Redo・保存・左右反転・再生成が容易。ラスタライズは自前ソフトウェア実装 (Canvas 非依存) なので Node でテスト可能。
3. **ステージは宣言的データ (StageDef)** — 衝突ジオメトリと見た目を同じ定義から生成。ボット用ルートヒントも同梱。
4. **能力 → 挙動の写像は純関数** — `computeStats()` / `statsToParams()` / `applyLevel()` をユニットテスト。
5. **保存・ランキングは抽象化** — IndexedDB → localStorage → メモリの順にフォールバック。ランキングは `RankingBackend` インターフェース。
6. **ゲーム時間は単調増加時計** — `performance.now()`。操作不能時間 (ロード/演出/ポーズ/バックグラウンド) は除外。

### 座標・単位
メートル、Y-up、固定 60Hz 物理 (1/60 s)、描画は補間。標準キャラの高さ ≒ 1.6m、重力 -24 m/s²。

## 5.5 敵と見た目の作り込み (PHASE 17: STAGE 1 で試作)

* **敵** (`src/game/enemies.ts` + `GameSim`): 5 種類 (blob / hopper / spiky / chaser、STAGE 2 から armor = カタマル)。巡回する敵は位置が経過時間の関数 (移動床と同じ = 決定的)、chaser だけプレイヤーの位置で動く。判定は円柱 × 円柱。優先順位は ACTION → ふんづけ → 接触ダメージ。ACTION は `attackPower >= toughness` で倒す (木箱と同じ仕組み)。ふんづけは落下中 (vy <= -1) に足が敵の上の方に来た時 (トゲの敵は不可)。復活 (`respawn`) では、チェックポイントを通った時点で倒していた敵 (`committed`) は戻らず、それ以外は元に戻る。チェックポイントで HP 全回復 (`heal` イベント)。ノックバック (`knockAway`) は足場の縁までの距離を測って弱める。ゴール後は敵・罠の判定を止める。ボットは「前方で届く範囲の、倒せる敵に ACTION」で対応する。
* **見た目** (すべてコードだけ。Blender や外部素材は使わない): ① 表面の模様 (`surfaceMaterial.ts`: ワールド座標の手続き的な模様をトゥーン材質に注入。草・石・木・レンガなど。画質 LOW では無効) ② 小道具の道具箱 (`stages/decorKit.ts`) と、コースの形に合わせて置く `stages/meadow.ts` (縁の草・花・柵・浮島・雲海・丘) ③ 看板 (`signView.ts`) ④ 空気感 (`ambientView.ts`: 花粉・花びら・ちょうちょ) ⑤ 太陽 (`theme.skySun`: 見下ろし気味のカメラの視界に入るよう、光の向きとは別に地平線近くへ置く。深度テストあり)。敵はパーツを 1 体ごとに結合して軽くしている (目・足・影は別メッシュ)。看板は文字面が走りながらでは読めないので、**近づくと画面上部に説明カード (`Hud.hint`) を出す**のが本体 (`SignDef.hint`。`{move}/{jump}/{action}` は端末の操作名に置き換わる = `src/input/labels.ts`)。表面の模様のシェーダーは、画質「ひくい」では別プログラム (模様なし) になり、遠くでは薄れ、動く床の上ではその床の座標で描く。

## 5.6 フィールド型ステージ (PHASE 18: STAGE 1 で試作)

ユーザーの評価 (「ほぼ一本道ではなく、マリオ 64 以降のように広いフィールドを駆け回り、必要なアイテムを集めたりボスを倒したりしてクリアしたい。タイムアタックで攻略を試行錯誤できる自由度が欲しい」) を受けて、STAGE 1 を直線コースから作り替えた。

* **地形** (`stages/terrain.ts` / `terrainBuilder.ts`): 高さフィールド (`TerrainDef`: 頂点の高さ + 地面の種類)。当たり判定は Rapier の `heightfield`、見た目 (`render/terrainMesh.ts`)・敵の足元・小道具の置き場所は**同じ高さデータ・同じ三角形の割り方** (セル内の対角線は (ix+1, iz)–(ix, iz+1)。実験で確認し、`tests/physics/terrain.test.ts` が 400 点で Rapier のレイキャストと 2cm 以内で一致することを保証) から求める。配列は `idx = ix * (nz+1) + iz` (Rapier と同じ並び)。`TerrainBuilder` は丘・台地・くぼみ・道 (高さを均して土の色に)・島の縁 (崖)・ノイズ・色塗りの道具で、乱数を使わず座標だけで決まる。箱・動く床・水・風・敵などは地形と混在できる。
* **クリア条件** (`ObjectiveDef` + `PickupDef`): `collect` = 星を required 個集めるとゴールが開く (総数は pickups の数。全部集めなくてよい)。`GameSim` が取得 (`pickup` イベント)・ゴールの開閉 (`goalOpen`、閉じている間にゴールに触れると `goalLocked`)・取った星の保持 (やられても戻らない) を持つ。条件のないステージ (S4・S5) は従来どおりゴールに着けばクリア。ボスを倒す形式は未実装。
* **敵の足元**: `EnemyDef.onTerrain` の敵は、毎ステップ地形の高さに沿う (跳ねる敵は地面 + 跳躍)。
* **描画**: 静的な物 (地形・箱・装飾) は空間 (xz) の区画ごとに結合したメッシュ (`stageMesh.buildStaticStageChunks` / `terrainMesh.buildTerrainChunks`) にして、**区画ごとに視錐台カリング + 距離カリング** (霧の距離 × 画質の見える距離)。装飾の `extra` は画質「低」で描かず、`far` (雲海・遠い丘・空の雲) は 1 メッシュにまとめて常に描く。星 (`pickupView.ts`) は星・縁・光の柱の InstancedMesh 3 つ。ゴールは条件を満たすまで灰色 / 開くと金色に脈打つ。地面の模様は草の色の所だけに葉と花を描く (土の道・砂・岩にはつぶつぶ)。
* **ミニマップ** (`ui/minimap.ts`): 地形を 1 枚の絵にしておき、毎フレームはカメラの向きが上になるよう回して貼る。星・ゴール・チェックポイントを印で出し、窓の外の物は縁に寄せる。地形のあるステージだけ表示。
* **ボットのルート**: ウェイポイント列のまま。STAGE 1 は `main` (誰でも: 5 つの星) / `power` (木箱の遺跡: 攻撃力 ≥ 0.95) / `jump` (浮島の階段: SPEED/JUMP) の 3 本。ビルドごとに通れた中で最速のルートを採用する (バランス計測)。
* **垂直な崖は箱で作る**: 格子 (2m) の高さフィールドでは崖が 50〜68° の斜面になり、ジャンプしながら押し込むと登れてしまう。登らせたくない崖 (崖の丘の塔など) は、地面から立つ箱 (ブロック) で作る (`stage1.ts` の `cliffTower`)。`tests/stages/stage1.test.ts` が、行き止まりで自動ジャンプし続けるボットで直登できないことを検証する。
* **星の出現条件 (`PickupDef.appearAfter`)**: 敵のいる場所の星を駆け抜けて取れないよう、その場所の敵 (EnemyDef.id) を全員倒すまで星が現れない。シミュレーション: `GameSim.revealed` (一度現れたらやられて敵が復活しても消えない)・`isPickupAvailable` / `pickupLockedRemaining` (あと何体)・`defeatEnemy` の直後に判定して `pickupAppear` イベント。取得判定 (`checkPickups`) は現れていない星を飛ばす。表示: 封印された星 = 薄い灰色の星だけ (光の柱なし、ミニマップは点線の輪郭) → 現れた瞬間にぽんと大きくなり光の柱が伸び、光の粒が弾ける (`PickupView.onAppear`)。UI: 倒すたびにトースト「あと n 体」・現れたらトースト・ポーズの星の一覧に 🔒 と残りの数。STAGE 1: 風車の丘 3 体・花畑 4 体 (ピョンタ)・広場 4 体 (チェイサー 2 体 + 番人のプルン 2 体)。封印の見せ方: 灰色の星 (不透明度 0.85) + 低い灰色の柱 (6m)、ミニマップは点線の星と、守っている敵の赤い点。星のそばに来ると「あと n 体」のトースト (同じ星では 6 秒に 1 回)。条件の敵が 1 体もいない星 (id が存在しない・空) は最初から現れている (永久に封印されない)。条件に入れる敵は踏みつけで倒せる種類だけ (トゲマルは攻撃力が足りないと倒せず、星を永久に封印してしまう。`tests/stages/validate.ts` が検査)。星の id は `star-meadow` のような固定の名前 (敵や飾りを足す順が変わっても、保存した星ごとのスプリットがずれない)。ボット: `WaypointDef.clear` (敵の id の列) で、全員倒すまで一番近い敵を追いかけて攻撃 (最大 60 秒。攻撃しない受動プレイは倒せずに諦める)。測定 (戦う設定のボット、本道): STANDARD 63.6 → 77.8 秒、SPEED 51.8 → 65.2 秒、HEAVY 79 → 96.4 秒、EXTREME → 104.0 秒 (被弾 0・死亡 0)。
* **ミスの時間加算** (`timeattack/penalty.ts`、`StageDef.missPenaltySec`): 落下・ダウン・ポーズからの「チェックポイントから再開」のたびに、max(最低秒数, ミスした場所からチェックポイントまでの水平距離 ÷ 戻りの速さ) (最大 25 秒。戻りの速さ = ビルドの最高速度の 85%、標準で約 6m/s) をタイムに加える。ポーズ画面の再開ボタンに見積りを出す (`respawn` イベントの `dist`)。批評で、広場の星を取ったあとに再開して帰り道を省くと、本道が 7〜13 秒短くなると測定されたため (固定 5 秒では足りない)。STAGE 1・2 (最低 3 秒)。
* **星ごとのスプリット** (`StageRecord.bestSplits`、`timeattack/splits.ts`): `pickup` イベントのたびに、タイマーの経過 (ミスの加算を含む) を `StageSession.splits` に記録する。`SessionDeps.bestSplits` (これまでのベストの走り) があれば、トーストに差を出す (`formatSplit` / `formatSplitDelta`)。結果は `StageResult.splits`。`Profile.recordClear(stageId, timeMs, splits)` は**ベスト更新の時だけ**星の時刻を差し替える (星の記録が無い走りでベストを更新したら、食い違うので古い記録を消す)。保存 (`normalizeStages`) は、不正な要素・重複・範囲外 (0〜2 時間) を捨て、32 個まで、ベストが無ければ読み込まない。スキーマ番号は変えない (追加の任意項目)。ゴースト (ベストの走りの影) は未実装。
* **カメラ**: 後ろへの回り込みに加えて、進行方向が回る速さ (0.5 秒ならした値・上限 1.6rad/s) の 0.4 倍をカメラに先回りさせる (大きくすると塔で遅れにくいが、スティックを傾けたままにした時の自励回転が 1/(1−係数) 倍に強まる。0.7 では 3.3 倍だったので 0.4 に)。理想円 (半径 12m) で、進行方向の真後ろからのずれが 0.64 → 0.43rad (半径 6m は 1.28 → 0.76)。直進・一瞬の方向転換・手動操作の直後では変わらない (`tests/game/camera.test.ts`)。
* **ゴールの光の柱**: 高さ 44m・霧の影響なし・開くと明るく (透明度 0.5)・輪も大きく。ゴールの周辺 (約 90m 以内) からは開いたことが分かる (既定のカメラは仰角が小さく、スタート付近の約 150m からは柱の上が画面外になる。遠くはミニマップの印で)。
* **作り込みの原則** (`stages/fieldKit.ts`): 置く場所を (x, z) で指定すると高さは地形から決まる (坂の上に浮かない)。`tests/stages/validate.ts` が、全ステージ共通で、危険物・動く危険物・敵・星の足元に床があることを検査する。

## 5.7 自由なキャラクター (PHASE 19: 自由スケッチ + ふくらませた立体)

ユーザーの評価 (「人型しか作れない。どのパーツを描くか選んで、足が 4 本の動物や腕が 4 本の阿修羅も作れるようにしたい」「平面に描いたパーツが奥に伸びただけの立体はイマイチ」) を受けて、キャラクターの作りを 2 つ変えた。

* **データ (`drawing/model.ts`): パーツのリスト**。`DrawingData { v: 2, parts: PartSlot[] }` (先頭は必ず胴体)。`PartSlot = { id, kind, view, side, pair, flip, mount, ops }`。
  * `kind`: body / head / arm / leg / tail / wing / ornament (角・耳)。上限は種類ごとのスロット数 (腕 4・脚 4・飾り 3・他 1) と全体 12。腕/脚のスロットを複数持てば (ペアなら 1 スロットで 2 本) 4 本・6 本・多足になる。
  * `view`: 絵の向き (`front` 正面 / `side` 横向き)。**パーツごとに選べる**。胴体が横向きなら四足の動物の形 (絵の右が前)、正面なら人型。
  * `pair`: 左右 (または奥手前) のペア。1 枚の絵を鏡像にして 2 本にする (描くのは 1 回)。`side` (L/R/C) は単体のとき。`flip`: 絵を左右反転して使う。
  * `mount`: つなぐ位置 (親パーツの絵の上の (u, v))。`null` なら自動 (種類・向きごとに根元の位置を決める)。エディタの「つなぐ位置」で手動指定できる。
  * v1 (固定 6 パーツ) の保存データは `upgradeLegacy` で変換 (左右コピー ON → ペア、OFF → 左右の単体)。`sanitizeDrawing` が v1/v2 を受け、不変条件 (胴体が先頭・id が一意・上限) を守る。保存スキーマは 1→2 に migration (`save/schema.ts`)、`STAT_FORMULA_VERSION` を 2 に (能力は読み込み時に再計算)。
* **配置 (`character/layout.ts`)**: `computeLayout` が全パーツの置き場所を決める。親 (胴体/頭) の絵の中の根元 (帯の中の最も内側の点) と、パーツ自身の根元を重ねる。人型の自動配置は旧実装と**数値まで同じ** (能力値の一致をテストで保証)。横向きの胴体では、絵の水平方向が前後 (z) になり、ペアは奥/手前 (x = ±) に振り分ける。正面の胴体に複数組の脚/腕を付けると奥行きにずらして並べる。
* **ふくらませる (`character/partGeometry.ts`)**: 輪郭を押し出すのではなく、マスクを**ふくらませて丸い塊**にする。パーツの内側の「中心からの距離」が高さになるよう、ポアソン方程式 ∇²h = −2 (境界で h = 0) を解いて h を求め、z = K√h (K = 1.15 × 種類ごとの係数。翼は薄く 0.45) の面にする。面は表裏を共有した輪郭でつなぐ (隙間なし)、法線は滑らか、テクスチャは絵の平面投影 (見えるのは描いた絵そのもの)。細い腕は細い円柱状に、大きい胴は大きな丸みになる。三角形は 1 パーツ約 1 万以下に抑える (格子の数に上限)。
* **輪郭線**: 絵の黒い縁取りは、色の領域として検出して縁の帯を内側の色で置き換え (`cleanPart.stripOutline`)、代わりに**視線に対して縁の側になるほど暗くなる** (フレネル風) シェーダー (`render/toon.ts` の `characterMaterial`) で表現する。立体の縁が黒く見えるが、絵に太い線を引くとその厚みが膨らんで黒い帯になる問題を避けている。
* **自由度 (PHASE 19c)**: 飾りは `onBody` で胴体にも付けられる (背びれ・甲羅。単体の飾りが複数なら背中に沿って並ぶ)。パーツの複製 (`EditorState.duplicatePart`: 種類・向き・ペア・絵を写し、取り付け位置は自動)。しっぽ・翼は 2 スロットまで (2 つ目以降は自動で上下・左右に振り分けて重ならない)。
* **足並みと接地 (PHASE 19c)**: 足並みのグループは、同じ側の手足を**位置 (前から何番目か)** で数えて決める (単体スロットを 左・右・左・右 と並べても、対角が同位相になる)。脚の振れ角は、1 周期に進む距離から決めた角度と従来の経験式を半々で混ぜ、足の滑りを減らす。**横向きの胴体 (四足など) は前傾を 1/4 に弱める** (長い胴体を傾けると後ろ脚が浮く)。しっぽが地面に潜る時は、潜らない向きへ持ち上げる (立ち姿で潜るしっぽの大きな補正は、作る時に 1 回だけ決める固定角にして、毎フレームの補正は小さな範囲の追従に限る = 状態が変わっても反転しない)。
* **腕の無い生きもの**: 腕の太さ/面積の特徴量を最低値ではなく −0.55 に、さらに**頭の大きさ・飾り (角) の大きさを突進力 (`ram`) として POWER に加える**。標準的な四足は POWER 約 65 (腕のある人型より弱い)、大きな頭 + 角 + 赤で約 99 (木箱 toughness 0.95 を壊せる。代わりに SPEED/JUMP が落ちる)。
* **法線**: 頂点法線を 2 回、隣の頂点と平均してなめらかにする (`partGeometry.smoothNormals`)。輪郭の頂点は前面と背面が共有するので、前後の法線が混ざって丸い側面になり、縁を暗くするシェーダーで縁に出る点線・黒い先端が減る。
* **輪郭の線の除去の補足**: 帯は縁から「線の太さ × 1.5 + 3」の深さまで。それより内側の、輪郭と同系の色の領域 (縞・ぶち・黒髪・黒い靴) は絵の一部として残す。先端 (楕円の左右の端など) では、レベル (縁からの距離) がほぼ同じ画素が並んで内側の色を受け取れず線が残るので、置き換え済みの画素から受け取る形で複数回繰り返す。
* **エディタの低い画面 (高さ 460px 以下)**: 幅 740px 以上 (844×390 など) では右の欄を 2 列にし (左 = 大きなプレビュー・パレット・太さ、右 = パーツの設定)、スクロールなしで全部の設定が見える。描き方の説明はヒントの行の代わりに、紙の上に数秒だけ出す (つなぐ位置の説明は出し続ける)。
* **背中側の絵 (`character/backTexture.ts`)**: 正面の絵のパーツは、背中側のテクスチャから顔などの細かい描き込みを消す。そうしないと、後ろから追うカメラには「こちらを向いたまま後ろ歩きしている」ように見える (旧実装から続いていた問題)。テクスチャを色の領域に分け、パーツの面積の 5% 未満の領域 (目・口・ボタン・アンチエイリアスの混ざった色) を、いちばん近い大きな領域の色で塗りつぶす。大きな領域 (髪・服・靴など) は残し、1 色に均す。消す物が無ければ前と同じ絵 (材質は 1 つ)。ジオメトリは前面・背面の三角形を材質グループ 0/1 に分けてあり、背中側の絵があるパーツだけ 2 材質のメッシュ (描画呼び出しが 2 回) になる。横向きの絵のパーツは、反対側にも同じ絵が出る (顔つきの四足の顔が反対側にもある)。
* **アニメーション**: 脚・腕・しっぽ・翼・飾り・頭をパーツごとに駆動する。歩行は脚を組に分けて交互に動かす (2 本 = 左右交互、4 本 = 対角のペア (トロット)、6 本 = 三脚歩行)。腕が 3 組以上のときは余った組が広がって揺れる。翼ははばたき、しっぽは振る。
* **能力**: 特徴量に「腕/脚の本数」「翼」「しっぽ」「飾り」が加わった。腕が多いほど POWER、脚が多いほど SPEED/安定、翼は JUMP を助け WEIGHT を下げ、飾りは DEFENSE、しっぽは安定。腕が無い生きものは、腕の太さ/面積を最低値ではなく −0.55 (頭突き・体当たりで戦える程度) として POWER に張り付かないようにした。予算の正規化は変わらない。
* **スケッチ刷新 (PHASE 21: 「ドラゴンとオオカミの再現テスト」の反省)**。再現テスト (`docs/PROGRESS.md` PHASE 21) で、細部が消える・奥行きが出ない・色が選べない、という限界が見つかった。
  * **パーツごとの大きさ `PartSlot.scale`** (省略 = 1。胴体には使わない): 絵を貼る倍率。`layout.ts` の全寸法 (関節の位置・脚の長さ・頭の高さ・飾りの位置) に `PlacedPart.k` をかける。`partGeometry` と `measure.ts` (能力値の入力) も同じ倍率。小さな部品は、紙いっぱいに描いて 0.3 倍で貼れば、細かく描ける。**厚み `PartSlot.depth`** はふくらませの高さ (K) にかかる。
  * **もう一つの向きの絵 `PartSlot.alt`** (`character/profile.ts`): 輪郭から**厚みの形** (`DepthProfile`: 1 枚目の各行 [翼・横向きのしっぽは各列] の、厚み方向の範囲 [中心 ± 半分]) を作る。`partGeometry.applyDepthProfile` が、ふくらませた形の z を行ごとに「中心 + z × (半分の厚み ÷ その行の z の最大)」に作り直す (輪郭の頂点 z = 0 は中心の位置に来る = 前面と背面で共有したまま水密)。前かがみ・そり・太さの変化がこれで出る。向き: 正面の絵のパーツ = 絵の右が前、横向きの絵のパーツ = 絵の左が +t (キャラクターの右)、翼 = 上が前、横向きのしっぽ = 下が +t。**横を向いた面の色**は、頂点属性 `altUv` / `altW` と `characterMaterial(…, altMap)` のシェーダーで、alt の絵から取る (法線が横を向く度合いで混ぜる。横向きの絵のパーツは、表と背中側を横に並べた 2 枚組)。
  * **後ろから見た絵 `PartSlot.back`** (`prepare.ts mergeBack`): 左右反転して 1 枚目の座標に合わせ、絵のある所は裏の絵の色、無い所は従来の背中側 (顔などを消した絵 / 1 枚目と同じ) で埋める。
  * **輪郭の線の除去の見直し (`cleanPart.stripOutline`)**: 輪郭の太さを、面積 ÷ 周長ではなく、**縁から内側へ各深さで「輪郭の色に近い画素」が半分以上を占める深さ**で測る。以前は、輪郭の色が塗りの色に近い (差 56 未満) と、塗りまで輪郭と見なして帯が深くなり、パーツ全体が別の色に塗り替わった (オオカミの白い脚が青一色)。帯の深さは「太さ + 2」。`MIN_FEATURE` 0.05 → 0.034 (細いとげ・毛束が太りすぎない)、最小の線の太さ 0.012 → 0.006。
  * **エディタ**: 右の欄の並びを、色・太さ (いちばん上) → パーツの設定 → 全体像の小窓 に。**実機で色が選べなくなっていた不具合**は、全体像の canvas (220×220) の元の大きさが欄の並びに影響して色の欄を押し出していたのが原因で、小窓の枠を大きさの決まった箱にして canvas を絶対配置にした。パレットは `auto-fill` (欄の幅に収まる列数。固定の列数は、狭い欄で隣の欄に重なる)。好きな色は HSV の四角 + 色相の帯 (`colorPicker.ts` / `core/color.ts`)、最近使った色は localStorage、スポイトは `Tool 'pick'` (塗り・スポイトは指を離した時に行う = 2 本指の 1 本目で塗らない)。紙の拡大は `.ed-view` の CSS 変換 (ピンチ / ホイール / ボタン、右・中ボタンのドラッグで移動。2 本目の指が触れたら描きかけの線は取り消す)。ページ (1 枚目 / もう一つの向き / 後ろから見た絵) は `EditorState.page` で、履歴 (Undo) と ラスタのキャッシュはページごと。「プレビュー」は `CharacterPreview3D` (開く間だけ WebGL を持つ。使えない端末では従来の 2D)。
* **もよう `PartKind 'decal'` (PHASE 21b, `character/decal.ts`)**: 顔を頭に描くと滲む問題 (3D 用の絵は紙全体で 192×192。紙の 45% に描いた顔は目が 8 テクセルで、バイリニア補間とミップマップでぼやける) への対策として、**立体にしない・形に関係しない絵**を貼り先の表面に貼る種類を足した。
  * データ: `PartSlot { kind: 'decal', ops, mount (貼る位置 = 貼り先の紙の上の (u, v)。省略 = 貼り先のシルエットの重心), scale (貼り先の紙の幅に対する倍率。足すと 0.5), pair (左右にも貼る), onBody (胴体に貼る。省略 = 頭があれば頭), flip }`。`view` / `depth` / `alt` / `back` は使わない。上限 4 つ。
  * 絵は `decalTexture`: ラスタをそのまま (384×384) 貼る絵にする。立体化の整形 (輪郭の除去・背中側の簡略化・ふくらませ) を通さない。透明な画素は近くの色でにじませ (縁の黒い筋を防ぐ)、縁の 1 画素は透明にする。
  * 貼る面は `buildDecalPatches`: **貼り先のジオメトリの三角形をそのまま写し** (絵の範囲 [正方形] に重なる三角形だけ)、位置・法線・頂点の色は貼り先と同じで、法線の向きに表面から少し浮かせる (縁では浮かせない)。最初はレイを当てて格子のパッチを作ったが、トゥーンの陰の境目が貼り先とずれて、目の上にぎざぎざが出たので、貼り先と同じ三角形を使う方式にした (陰影が完全に一致)。UV は位置から平面投影 (範囲の外は縁の透明な画素)。材質は `characterMaterial` (縁の暗さは貼り先と同じ) + `transparent / depthWrite: false / polygonOffset`。貼り先のメッシュの子にするので、頭のアニメーションといっしょに動く。
  * ペア: 正面の絵の貼り先では、シルエットの重心について左右対称の位置に反転して貼る (中心にあるもようは 1 面のまま)。横向きの絵の貼り先 (四足の体) では、反対側の面 (背面の三角形) に反転して貼る。
  * 形・能力に関係しない: `layoutOfPrepared` / `layoutFromRasters` が配置の入力から外す。色の計測 (`measureColors`) には入る (何も描いていないもようは入らない)。何も描いていないもようは貼らない (既定の形で代用しない)。
  * エディタ: パーツの設定は、左右にも貼る / 頭に・胴体に / 大きさ / 左右反転 / 貼る位置 / 複製 / 消す。「貼る位置」では、貼り先の絵の上に、貼る絵を実寸で重ねて見せる (ペアの相手も)。2D の全体像にも重ねて描く (`CompositePreview.drawDecals`)。
* **前後のずれ `PartSlot.forward` (PHASE 22)**: 胴体の紙の幅を 1 とした長さ (正 = 前、範囲 ±1)。正面の絵の胴体につくパーツだけ (`builder.zOf`)。「もう一つの向きの絵」の前後のずらしは、パーツ自身の紙の半分までしか届かない (頭の紙は小さく描きたいので、首を前に出した姿勢には足りない) ため。頭の子 (角・耳) は頭のずれについていく。使い方: パーツの横から見た絵の紙の中央を見本の「そのパーツの前後の位置」に置き、`forward = (体の軸の位置 − そのパーツの紙の中央の位置) ÷ 胴体の紙の幅` を設定する (ドラゴンの再現で使った)。
  * しっぽ・翼の前後の位置は、胴体のメッシュの実際の前後の範囲から決める (`builder.zBase`: しっぽ = 後ろの面 + 厚みの 5%、翼 = 胴体の中心 − 厚みの 12%)。以前は「胴体は前後に対称」を前提に厚み × −0.45 / −0.12 だったので、前かがみの胴体 (中心がずれる) で、しっぽが胴体から離れた (対称な胴体では同じ値)。
  * 紙の外に出た線は、紙のふちで切れて輪郭が閉じず、塗りが失敗する (紙のふちに触れた領域は塗られない)。横から見た絵は、パーツの紙 (幅 = 大きさ) の内側に収める。
* **傾き `PartSlot.tilt` (PHASE 23)**: `{ yaw (ひねり), pitch (おじぎ), roll (かたむき) }` 度 (整数・±120・0 の軸は持たない)。関節 (ピボット) を中心に、**キャラクターの向き** (x = 左、y = 上、z = 前) で回す。順序は ひねり → おじぎ → かたむき (`Euler 'YXZ'`)。`builder.attach` が、メッシュの回転を「傾き × 絵の向き」にする (横向きの絵の 90° 回転の後にかかる)。**ピボット自体は回さない** (アニメーションがピボットの回転を毎フレーム決めるので、静的な傾きを混ぜると衝突する)。ペアの相手は ひねり・かたむき が逆 (左右対称。正面の絵の鏡像側は、反転した絵にこの回転がかかる)。単体の右側スロットは反転しない。頭の傾きは、頭の子 (角・耳) の**位置と向き**にも伝える (子はピボット単位で頭のグループにぶら下がるので、頭のメッシュだけ回すと取り残される)。もようは貼り先のメッシュの子なので自然についていく。向き: 主の側 (左) の翼は、ひねり + で先が後ろへ、かたむき + で先が上へ。おじぎ + で上が前へ。胴体には付けない。
  * 2D の全体像 (`CompositePreview`) と「つなぐ位置」には反映しない (3D のプレビューで見る)。
  * エディタ: 「⚙ 大きさ・姿勢」の欄 (大きさ・厚み・前後・ひねり・おじぎ・傾き) にまとめて開閉。何か設定してあれば最初から開く。行が多いので、`.ed-part > *` は縮まない (縮むと重なって読めない)。
* **お手本 (`ui/editor/refImage.ts`)** (**今は止めてある**: `EDITOR_FEATURES.referenceImage = false`。`features.ts`。紙に canvas も操作も付けず、読み込み・描画も入口で戻る。配線は `tests/ui/editorFeatures.test.ts`): 端末の画像を `createImageBitmap` で読み、長辺 1400px に縮めて持つ。紙の下の専用の canvas (`.ed-ref`) に、位置 (中心)・大きさ (紙の幅に対する幅)・濃さ (4 段階) で描く。パーツ・ページごとに位置を `Map` で覚える (保存しない・送らない)。✥ の「動かす」モードは、紙のドラッグで絵ではなくお手本を動かす (拡大の 2 本指は従来どおり)。位置・大きさの計算は DOM に依存しない関数 (`tests/ui/refImage.test.ts`)。
* **エディタ (`ui/editor/`)**: 上部のパーツチップ (胴体・頭・腕…・＋足す)。新規時は「ひな形」(人型/四足/阿修羅/鳥/虫/ゆるキャラ/胴体だけ) を選ぶ。右パネルでパーツごとの正面/横向き・ペア・向きの反転・つなぐ位置・削除。キャンバスの薄いガイドと説明文はパーツの種類と向きで変わる。「プレビュー」は 3D 化と同じ `computeLayout` の結果で描いた 2D 合成。

## 5.8 STAGE 2 強風の谷 とカタマル (PHASE 24 / 24b: 2 つ目のフィールド型ステージ)

STAGE 1 の評価の流れで、STAGE 2 を直線コースからフィールド型に作り替えた。ユーザーの方針 (「STAGE 1 でピョンタを硬くせず、ステージ 2 以降で、ACTION では倒せない敵を実装する。ただし同じ敵なのに倒し方が変わるのは避ける」) に沿って、新しい敵の種類を足した。公開後、批評者 2 体 (デザイン / 技術) が「要修正」とし、PHASE 24b で作り直した (経緯は docs/PROGRESS.md)。

* **構成** (`stages/stage2.ts`): 赤い台地の浮島 (R = 100m、中心 (0, 32)) を、深い谷 2 本 (`TerrainBuilder.chasm`: 中心線の折れ線・半幅 16m・縁 5m・底 −40m = 奈落ライン (−30) の下) が東西に断ち切り、**南の岸 → 南のつり橋 → 中の台地 → 北のつり橋 → 北の岸** の 3 つの地面になる。地形を歩いて谷を越える道がないことは、`tests/stages/stage2.test.ts` が頂点の格子を塗りつぶして検査する。ラクガキ星 8 個・必要 5・チェックポイント 14・看板 12・敵 16・風域 20・飾り 約 1,300。**星は、どれも道の途中ではなく寄り道の先** (テストが、道から 12m 以上を検査)。戦わずに取れる星 5 個 (風見・風の祠・枝橋 2 つ・回廊)、敵を倒して出す星 3 個 (谷口・山頂・突風の広場)。
* **つり橋** (`bridge()`): スパン (風の細い橋: 5 × 5m) と避難所 (3 × 9m) を交互に 6 スパン (全長 45m)。風域は `FieldKit.wind` (AABB。幅はデッキ + 4m)。スパンごとに、横風 (隣と逆向き)・突風 (周期 6 秒、吹く 3.8 秒・止み間 2.2 秒)・位相をずらす (`BRIDGE_STAGGER`)。**風の強さはスパンごとに違う** (`SPAN_WIND`: 南の橋は南から北へ 11・14・14・13.5・13.5・10、北の橋は 10・13.5・14・12・14・11 m/s)。風の中を渡れる限界は、体重の軽さの順 (風で流される速さ ≦ 最高速度の 93%): 14 と 13.5 は HEAVY / EXTREME だけ / 12 は JUMP・POWER から / 11 は STANDARD から / 10 は SPEED も。→ 体重ごとに、待つスパンの数が 10 (SPEED) → 8 (STANDARD) → 6〜7 (JUMP・POWER) → 0 (HEAVY・EXTREME) と**段階的**に変わる (2 本の橋の合計) (全部が同じ 14 m/s だと、押し切れる重さの境目で、わずかな体重の差 (+5%) で時間が 3 割変わった)。橋の途中 (2 つ目と 4 つ目の避難所) にチェックポイント。
* **枝橋**: 2 つ目の避難所から横へ (南の橋は東、北の橋は西): 風の吹くデッキ (6m) → 風のない足場 (3m) → 風の吹くデッキ (6m) → 風のない足場 (星)。風は橋に沿った向き (= 枝橋には横風。2 つのデッキは風向きが逆)・突風 (周期 6.4 秒)。軽い体は、足場ごとに止み間を待つので、往復で約 12〜18 秒かかる。風に強い体は約 9 秒。**軽い体には割が悪く、風に強い体には割がいい星**にして、体型ごとに最適な 5 個が変わるようにした。ボットの判断 (`calm`) は、足場 (風のない所) で待つ。
* **風の合図灯** (`WindDef.beacons` / `render/windBeacons.ts` / `game/wind.ts` の `calmRemaining`): 足場の柱の上のランプ (1 draw call の InstancedMesh)。赤 = 風が吹いている / 緑 = 止んでいて、渡るのに足りるだけ続く / 黄 (点滅) = 止んでいるが、もうすぐ吹く (残りが `need` 秒より短い)。橋のスパン・枝橋のデッキ・回廊の区画ごとに置く。風待ちが「ただ待つ」ではなく、リズムを読む遊びになる。 緑の長さは、止み間 − `need` (橋 1.2 秒 → 緑 約 1.0 秒 / 枝橋 1.5 秒 → 約 0.9 秒 / 回廊 1.8 秒 → 約 0.8 秒)。人の反応 (0.3〜0.5 秒) より十分長いこと・黄が長すぎないこと (`need` を、実際に渡る時間より少し長いだけにする) をテストが検査する。枝橋の灯は柱を高く (3.4m) して、橋の次のスパンの灯と見分けがつくようにした。
* **世界の時計を、READY → GO のあいだ止める** (`PlayScene.holdSim`): 風・巡回する敵・移動床は時計の関数なので、GO の瞬間は、いつも時刻 0 の状態になる (以前は、READY と GO の約 1.8 秒のあいだも時計が進み、フレームレートや読み込み時間で、GO の風のリズムが毎回少しずれた)。ボットの測定 (時刻 0 から走る) と実際のプレイが一致し、タイムアタックの風のリズムを覚えられる。
* **風のリズムと測定の教訓**: 隣のスパンとの位相のずれ `BRIDGE_STAGGER` で、軽い体の待ち時間が大きく変わる (次のスパンの止み間が、前のスパンの止み間より、ずれの秒数だけ早く始まる。ずれが小さいと、渡り終えた時には終わっていて、次の周期まで待つ)。現在は 1.5 秒。ボットは毎回同じ位相で走るので、風の周期との位相しだいで、同じ道でも時間が大きく変わる (運)。**バランスの測定は、スタートで 0 / 1.5 / 3 / 4.5 秒待ってから走る 4 回の平均** (`tests/stages/harness.ts` の `runStageAveraged`。`allStages.test.ts` は、周期的な風があるステージでこれを使う)。
* **向かい風の回廊** (`hall`): 短い通路 (長さ 28m)・2 区画 (突風 6 秒のうち 3.5 秒)・風は西向き 11m/s・壁ぎわの石柱とかがり火。ボットの「渡る前の判断」は、進む向きに対して風を**進行方向と横方向に分ける** (`Bot.decideCross`: 前進速度 = √(最高速度² − 横に流される速さ²) + 進行方向の流され。追い風なら速く、向かい風なら遅い)。係数は `player.ts` の `GROUND_WIND_FACTOR` を共有する。
* **風の祠**: 上面 4m の岩棚 (垂直な壁の箱)。南の面ぞいに階段 (1m × 3 段)、西面の手前に上昇気流 (押し上げ 5 m/s・高さ 7m)。重い体 (HEAVY / EXTREME) は押し上げが足りず、岩棚に届かない (階段は誰でも)。岩棚の上に、巡回するカタマル 1 体。
* **カタマル** (`ENEMY_SPECS.armor`): `toughness = UNBREAKABLE (99)` (攻撃力は 0.4〜2.4 倍の範囲なので、どのキャラの ACTION も届かない)・`stompable: true`・高さ 0.8m (低く、踏みやすい)・巡回 (速さ 1.3)。ACTION は既存の「攻撃力不足」の経路 (`guard`: 後ろへ弾かれ、直後に無敵) になる。踏めば、他の敵と同じ (`stomp`)。「同じ種類の敵は同じ倒し方」の方針: ステージ側の `toughness` 上書きは `validate` が禁止したまま。星の出現条件に入れられる敵は `killableByAll` (踏める種類) = カタマルは入れられる。見た目 (`enemyView.ts`): 青い鋼の低いドーム + ふちとこぶ + 顔と足。はね返された時は黄色い火花を大きめに出す。初めてはね返されると、トースト「硬い甲羅は、体当たりがはね返される　上から踏みつけよう」(4 秒に 1 回まで。木箱の「壊せません」とは別に数える)。スタートの近くに、星を守らない練習用が 1 体 (看板つき)。
* **地形の道具**: `TerrainBuilder.chasm` (深い谷)・`TerrainDef.palette` / `TerrainPalette` (ステージごとの地面の色。ミニマップも)・`FieldKit.wind`・`canyonKit.ts` (飾り: 地層の台地・岩の柱・アーチ・サボテン・アカシア・風見・吹き流し・つり橋の手すり・旗)。**丘は、平らな場所 (plateau) と道 (path) を作った後に重ねる** (先に丘を作ると、後から重ねた平らな場所や道に削られて、山頂が V 字の切れ込みと 60〜70° の壁になった。批評で発見)。頂上は、なめらかな山の形のまま (傾き 40° ほど)。
* **ボット**: `hunt` (WaypointDef.clear) は、ACTION が効かない敵 (攻撃力 < toughness で踏める) を**踏みつけ**で倒す (`stompJumpDist`)。`clear` が終わった直後に次のウェイポイントを飛ばす不具合を修正。折り返し (ほぼ逆向きのウェイポイント) の直後は、減速を「壁に阻まれた」と取り違えて自動ジャンプしないよう猶予をつけた (枝橋の足場で折り返して跳ぶと、風にあおられて落ちていた)。`stage2RouteFor(stage, 星の組み合わせ)` で、星の組み合わせから、地形の順にルートを組み立てられる (56 通りを全部測れる)。名前つきのルートは 6 本: `main` (戦わずに取れる 5 個) / `vent` (風の祠を上昇気流で: 重量型は届かない) / `wind` (風見・風の祠・枝橋 2 つ・山頂: 風に強い体と JUMP の最速) / `light` (谷口・風の祠・枝橋 2 つ・突風: 軽い体向け) / `quick` (風見・風の祠・山頂・北の枝橋・突風: STANDARD の最速) / `mixed` (風見・風の祠・南の枝橋・山頂・突風: POWER の最速)。
* **地形の検査** (`tests/stages/fieldChecks.ts`): ボットはジャンプの連打で急な斜面を登ってしまうので、地形の不具合 (壊れた斜面・島の外・谷の中にある敵) では失敗せず、見逃していた。そこで、地形そのものを検査する: 敵の巡回経路が立てる地面 (傾き 48° 以下) の上にあるか、チェイサーの範囲の立てない所が 3% 以下か、星・チェックポイントに傾き 50° 以下で歩いて行けるか。ルートの `calm` が指す風域の id が実在するかも、全ステージ共通の検査 (`validate.ts`)。
* **保存したベストの版管理**: `StageEntry.rev` (コースの版。作り替えて、これまでのベストが比べものにならなくなったら 1 上げる。STAGE 2 は 4・STAGE 3 は 3)・`StageRecord.rev`・`TimeAttackBest.revKey` (全ステージの版をつないだ文字列)。起動時に `Profile.dropStaleBests` が、版が違うステージのベスト・星ごとの時刻と、組み合わせが違う ALL STAGES のベストを捨てる (クリア済みの印・回数は残す)。捨てた時はトーストで知らせる。
* **バランス** (`tests/balance/allStages.test.ts`): 最速の道で、HEAVY 80・JUMP 82・EXTREME 83・STANDARD 88・SPEED 90・POWER 96 秒 (S2 のリーダーは JUMP と HEAVY。EXTREME が 3 位、SPEED は HEAVY より 13% 遅い)。経緯: 最初に広いフィールドに作ったところ、足の速い SPEED 型が全 5 ステージで最速になり、EXTREME が全ステージで最下位になった (広いフィールドは歩く距離が長く、足の速い体が有利になりすぎる)。そこで、歩く距離を詰め (3 つの地面に分けて、星を近くに寄せた)、橋を 12 スパンにし、風の強さを体重の段階に合わせた。風を止めた谷 (`buildStage2({ windScale: 0 })`) との差 (風のコスト) は、軽い体が 20 秒以上・HEAVY / EXTREME が 10 秒以内 (`tests/stages/stage2.test.ts` が検査)。星の組み合わせ (56 通り) を全部測ると、どの体型も、最速の 5 個の組み合わせが数通りあり (差 1〜5%)、風見・谷口・山頂・突風・枝橋のどれを取るかは体型で変わる。回廊は割が悪く、あまり選ばれない。

## 5.9 STAGE 3 水没神殿 (PHASE 25 / 25b: 3 つ目のフィールド型ステージ)

STAGE 3 を直線コース (大広間の仕切り壁 + ポンプ室) から、水を主役にしたフィールド型に作り替えた。STAGE 2 と同じ手順 (作る → 批評者 2 体 → 直す → 通ったら次へ) で進める。1 回目の批評は 2 体とも「要修正」(A: 星の選択が一本道 / B: 展望の塔から外壁に乗って、ステージの外へ出られる) で、25b で作り直した。

* **構成** (`stages/stage3.ts`、飾りは `templeKit.ts`): 高さ 12m の外壁で囲んだ神殿 (x ±54、z −76〜130)。南の前庭 (スタート) → **大広間** (水没。x ±24・長さ 78m、北と南に浜、床 −6m、水面 0m、陸 0.9m) と、その両側の**陸の通路** (x 27〜54) → 北の前庭 (ポンプ室) → **奥の院の関門** (z 82) → 奥の院 (ゴール。のぼり坂 3.6m)。地形は高さフィールド (`TerrainBuilder.set` で大広間・池・ポンプ室のくぼみを掘る。垂直な縁は壁の箱で塞ぐ)。ラクガキ星 8 個・必要 5・チェックポイント 11・看板 13・敵 13 (プルン 4・ピョンタ 4・カタマル 3・チェイサー 2)・水域 3。
* **星は地域ごと** (測定で決めた配置): 大広間 = 底の穴・浮島 / 西の通路 = 展望の塔 (階段 6 段、上面 6.9m)・貯水庫 (西の翼。プルン 2 + ピョンタ 1)・番人の間 (西の翼。チェイサー 2 + カタマル 1) / 東の通路 = 石の中庭 (東の翼。カタマル 2 + ピョンタ 1)・池の石柱 (池は南の浜からだけ入れる)・ポンプ室の高台。戦わずに取れる 5 個 = 浮島・底の穴・展望の塔・池の石柱・ポンプ室の高台、敵を倒して出す 3 個 = 貯水庫・石の中庭・番人の間。**星はどれも中央の線 (x = 0) から 12m 以上** (テストが検査)。
* **水の物理 (`game/player.ts` の水の部分。変更なし) で分かったこと**: 浮かんだ体は、頭 (身長の 0.9) が水面に出る深さで止まる (浸かり 0.9) → 水面から跳び上がれる高さは「跳躍の高さ − 身長の 0.9」で、背の高い体 (HEAVY・EXTREME: 身長 2.4m) は、水面から 0.5m 高い縁へも跳び上がれない。それで、石の台を **浅い棚 (水面 −0.5m) + 台 (水面 +0.5m)** の 2 段にした (`stand()`)。水底歩行 (`BOTTOM_WALK_*`) で、重い体は泳ぐより水底を歩く方が速い。
* **小さいドア**: 大広間の仕切り壁 2 枚 (z −6 / 14) に、小さいドア (まんなか。幅 2.2m・高さ **2.0m**) と大きいドア (横。幅 3m・高さ 3.3m。1 枚目は東 +18、2 枚目は西 −18) がある。小さいドアは ACTION で水底まで潜って通る (`WaypointDef.dive`)。通れる身長は、ドアの高さ − 約 0.025m (実測)。最初は 1.7m にしたが、境界 (JUMP 1.71m は通れず POWER 1.66m は通れる) が見分けられない (批評 A) ので 2.0m にした: HEAVY・EXTREME (2.4m) だけが通れず、ほかは通れる。小さいドアの近道は、遠回りの大きいドアより約 6 秒速い。
* **ポンプ室** (批評 B で作り直した): 水域 `pump` の水位が `level` (基準 −1.0・振幅 1.9・周期 10 秒) で上下し、**前庭の地面 (0.9m) を超えない** (水面の板が、壁なしで空中に浮いて見えない)。高台の上面は地面と同じ 0.9m で、**水位がおよそ 0.3m 以上 (周期の約 1/4) の時に、水面から JUMP (連打) して跳び乗る** (批評 B の実測: 連打すると、水面へ落ちる途中でも水中ジャンプが成立して、全ビルドが 0.15〜0.35m で乗れる。ジャンプ力が極端に大きい体は、ほぼ水位を問わない。ボットは JUMP を 1 回しか押さず、余裕を見て 0.5m (`PUMP.jumpLevel`) で待つので、背の高い体 (HEAVY・EXTREME) は水面から乗れず、石の通路を歩く)。**東の壁ぞいの石の通路** (入口の段 1.65m → 通路 2.4m → 降りる段 → 高台。長さ約 26m) を歩けば、水位に関係なく、だれでも確実に高台へ行ける (水面から跳ぶ近道より、往復で約 5 秒遅い。**水位の周期で時間が階段になる (待ちが最大 +10 秒の崖) のを、約 +5 秒に弱める**)。水位は時計の関数で、READY → GO のあいだ世界の時計は止まっているので GO の水位は毎回同じ。ボットは水面に浮かんで待つ (`waitWater`。水底で待つと、浮上のあいだに水位が下がって窓を逃した)。
* **奥の院の関門**: 石の壁 (高さ 11m) に、まんなかの**石の封印** (`BreakableDef` 1 つ: 4 × 3 × 2m・攻撃力 **1.25** = POWER (1.48)・EXTREME (1.32) が ACTION で壊せる。ほかのビルドは最大 1.04。ゲーム内の能力値では「攻撃力 (POWER) 133 以上」: 攻撃力 = (POWER / 100)^0.8 なので 1.25 ↔ 132.2。看板はこの言い方で書く (開発用のビルド名 HEAVY・EXTREME などはプレイヤーに見えない)。見た目は氷色 + 金の枠) と、左右 (x ±46) の通用口 (幅 6m)。全員が通る場所に置いた、攻撃力の高い体の近道 (通用口の遠回りは約 10 秒)。**封印を 1 つの大きな石にした理由**: 木箱を積んだ壁にすると、継ぎ目を足がかりに跳び上がって乗り越えられる (測定: 木箱 4 × 3 の壁に JUMP を押し続けると、足元が 5.6〜8.6m まで上がった。平らな壁・1 つの大きな箱は 2.1〜2.6m で登れない)。壁を高く (11m) したのも、縁に引っかかって跳び直す 2 段ジャンプで壁の上に乗れないため。`FieldKit.crateWall` に style を足し、`StageView` は壊せる箱を見た目 (style) ごとの InstancedMesh にした。
* **外壁の高さ (12m) と閉じ込めの検査**: 展望の塔の上面 (6.9m) から外壁 (最初は上面 6.9m) に跳び乗れて、神殿の外へ出られた (批評 B)。跳び上がれる高さは「頂点の高さ (jv²/2g) + autostep (0.3〜0.4m)」で、塔の星を取った位置から西へ押して連打するだけで起きた。外壁・翼の壁を 12m にして、`tests/stages/stage3.test.ts` に、塔の上から外壁へ走って JUMP を押し続ける検査 (6 ビルド + 跳躍力が極端に大きい体) を足した。同じ原理は STAGE 4・5 を作り替える時にも起きる。
* **ボット**: 水面で壁 (縁) に阻まれたら JUMP を連打して水から跳び出す (`blockedWater`)。水中の跳び出しの判定を、プレイヤー側の `WATER_JUMP_DEPTH` (0.92) と同じにした。潜る地点 (`dive`) は、目標の深さの ±1m に着くまで次へ進まない (浮く体が、穴の途中で到着扱いになって星を取り損ねた)。ルートは `stage3RouteFor(stage, { stars, trunk: 'hall' | 'west' | 'east', doors: 'small' | 'big', seal: 'break' | 'side', pump: 'swim' | 'walk' })` で、星の組み合わせ・本道・ドア・関門・ポンプ室から組み立てる。名前つき: main / small / west / west_dive / west_dry / east と、封印を壊す west_b / west_dive_b / west_dry_b。星の組み合わせ 56 通り × 本道 3 × ドア × 関門 × ポンプ室を全部測って (開始の位相 0 秒と 5 秒の平均。周期 10 秒の水位は、周期を 4 等分した位相 = `phaseDelays`)、体型ごとの最速に近い道を選んだ。

## 5.11 STAGE 5 巨人の塔 (PHASE 27 / 27b: 5 つ目 (最後) のフィールド型ステージ)

STAGE 5 を直線コース (PathBuilder: 4 つのフロアが一本道で、各フロアに近道) から、**階段状の塔**をまわって登るフィールド型に作り替えた。STAGE 2〜4 と同じ手順 (作る → 批評者 2 体 → 直す → 通ったら終わり)。これで全ステージがフィールド型になった。1 回目の批評は 2 体とも「要修正」(A 高: 戦わずに 5 個の星を取れるビルドがいない・木箱の扉の奥の段が重い体にはぎりぎり / B 高: 高い台が 2 階の壁の足がかりになる) で、27b で直した。

* **構成** (`stages/stage5.ts`、飾りは `towerKit.ts`): 広場 (地形。x ±84) の中心に、石の塊の塔。**階は四角いリング** (階 1〜4。上面の高さ 6 / 12 / 18 / 24m。外周の半幅 48 / 36 / 26 / 18m・内側は次の階の外周。外周の幅は 12 / 10 / 8 / 8m)、**山頂**は半幅 10m の台 (高さ 30m。ゴール)。壁は 6m の垂直な面 (石の塊の側面)。ステージ全体: 星 8・必要 5・チェックポイント 9・看板 11・敵 12 (プルン 6・ピョンタ 2・カタマル 2・チェイサー 2・新しい種類なし)・鉄球 5・上昇気流の柱 2・木箱 2。階ごとに石の色 (茶 / 砂 / 灰 / 青灰 / 山頂は氷) を変えて、どの階か分かるようにした。
* **長い道**: 次の階へは、**坂** (20m で 6m のぼる = 約 17°。幅 5m。次の階の壁ぞい) をのぼる。坂は階ごとに**南と北が入れかわる** (広場 → 1 階 = 南 / 1 → 2 = 北 / 2 → 3 = 南 / 3 → 4 = 北 / 4 → 山頂 = 南)。坂をのぼると台 (次の階の入口 = `ARRIVE_X`) に着き、そこは階の「着いた側」。次の坂は反対側にあるので、**リングを半周する** (東まわり / 西まわり。距離はほぼ同じ)。1 階 168m・2 階 124m・3 階 88m・4 階 56m。
* **近道 (ゲート)**: 着いた側の壁 (次の階の外周) の途中のしかけで、次の階の**坂の足元**に出る (壁をこえて、次の階の同じ側へ = 次の坂が目の前)。2 つ:
  * **1 階の南 = 木箱の扉 (C)**: 左右の壁 (8.5m) に囲まれた門。大きな木箱 1 つ (4.5m。攻撃力 0.95 以上 = ゲーム内の POWER 94 以上 = **STANDARD・POWER・HEAVY・EXTREME**)。壊すと、**1.2m の段が 5 つ** (外側が低く、壁に向かって高くなる。最後の段の上面 = 2 階の床)。SPEED・JUMP は壊せない。積み箱にしないのは、継ぎ目から登れてしまうため (STAGE 3・4 の教訓)。扉の上は石の横木 (前後に 0.2m 出す)。**段の高さ**: 最初は 2.0m × 3 だったが、跳べる高さが低い重い体 (POWER・HEAVY・EXTREME。ジャンプの高さ + 自動のぼり ≒ 2.1m) には、ぎりぎりで、ボットが「長押し → 角で止まった瞬間にもう一度押す」二度押しで抜けていた (扉の前から 2 階の床まで STANDARD 2.2 秒に対して 15.6 秒。人には厳しい = 批評 A 高)。1.5m × 4 にしたが、跳べる高さが最も低いキャラ (jump 45。ジャンプ + 自動のぼり ≒ 1.44m) が、2 階側から段を降りると、登り返せず閉じ込められる (批評 B 中 3) → **1.2m × 5 (奥行き 1.8m)**。テスト: 段を降りて、のぼって戻れる (jump 45・大きさ 1.0 / 1.5)。
  * **2 階の北 = 上昇気流 (U)**: 壁の手前 1.8m に、足元から 10m の気流の柱 (押し上げ **8.5 m/s**)。**走って気流に入り、ジャンプを押し続ける**と、6m の壁をこえて 3 階に降りられる。**STANDARD・SPEED・JUMP** (風の影響を受けやすい軽め〜標準)。POWER (最高 5.4m)・HEAVY (4.3m)・EXTREME (3.3m) は届かない。**風は「速度に足す」のではなく「位置を直接押す」型 (`player.ts`)**: 押し上げが強すぎる (9 m/s 以上) と、POWER も届き、浮いたまま着地せずにジャンプできなくなる。気流の中に立ち止まってから連打すると、体が弾むだけで失敗しやすい (批評 A)。押し上げ 7.5 m/s だと、STANDARD は走って入るジャンプの余裕が 0.5m 弱 (人の操作では 0/9)。8.5 m/s で 6/9 (押し続ける 2 つの操作は全部成功)。看板に「走って入って {jump} を押し続ける」と書いた。ボットは `WaypointDef.hold` (ジャンプを押し続けて、跳び上がるまでその場で待つ) で、接地の瞬間に跳ぶ。
  * 使えるビルドが違うので、**1 階の南 = 列 S / 2 階の北 = 列 N** の 2 つの道ができる: 列 S = 広場 → 坂 → 1 階の木箱の扉 → 2 階の坂 (すぐ) → 3 階 (南) → 長い道 (3 階・4 階) → 山頂。列 N = 広場 → 坂 → 1 階を半周 → 坂 → 2 階 (北) → 気流 → 3 階の坂 (すぐ) → 4 階 → 長い道 (4 階) → 山頂。**列 N に入るには、1 階を半周する (168m) ので、SPEED・JUMP は木箱が壊せない分、遅れる。**
* **体型ごとの寄り道の星** (批評 A 高: 「戦わずに取れる 5 個」が、体型で取れる数が違い、重い体は 3 個だけだった → **どの寄り道の星にも、だれでも行ける遅い道を足した**。S2 の「階段は誰でも、気流は近道」の型。近道は時間の節約になる):
  * **風の柱** (広場の南西。高さ 6m の柱の上に星): 南の上昇気流 = STANDARD・SPEED・JUMP / **西の長い坂 (20m) = だれでも**。
  * **1 階の高い台** (西の廊下。上面 2.8m の台): 直接跳び乗る = SPEED・JUMP のみ (ジャンプを押し続ける) / **南がわの段 (1.4m ずつ 2 段) = だれでも**。測定: 垂直な段に走って跳び乗れる高さは、STANDARD 2.4m・SPEED / JUMP 2.8〜3.0m・POWER 2.0m・HEAVY / EXTREME 2.0〜2.2m。**台には屋根 (東屋: 台の四すみの柱 + 屋根。頭上 3.0m) がある** (批評 B 高: 台の上から東へ助走して跳ぶと、4m 先の 2 階の壁 (12m。台の上面との差 3.2m) へ、跳躍力が極端に大きい体 (jump 148 以上・大きさ 0.6〜1.6) や足の速い体 (speed 222) が跳び乗れて、坂とゲートを飛ばせた (約 9 秒の節約)。屋根で台の上のジャンプをおさえた。屋根の上には、2 階の床から跳べば乗れるが、2 階から台の星に降りる寄り道になるだけ (往復で約 14 秒))。
  * **木箱の部屋** (広場の南東。壁 8.5m の小部屋): 南の扉の木箱 = STANDARD・POWER・HEAVY・EXTREME / **うしろ (北) の入口 (木箱なし) = だれでも** (部屋の東をまわる)。
* **星 8 個の構成**: 戦わずに取れる 5 個 = 風の柱・木箱の部屋・1 階の高い台・3 階の西の廊下・4 階の東の廊下 (**全ビルドが、遅い道で、戦わずに取れる。受動プレイ (fight: false) でクリアできるテスト**) / 敵を倒すと現れる 3 個 = 広場の東の庭 (チェイサー 2 + プルン 1)・3 階の東の廊下 (カタマル + ピョンタ + プルン)・4 階の西の廊下 (同)。守る敵は踏める敵だけ。廊下の星は、**その廊下を通る時に取れる**。通らない廊下の星は、往復の寄り道 (測定 +5〜+10 秒)。
* **鉄球 (動く危険物)**: 1 階の東西・3 階の西・4 階の東西の廊下を、幅いっぱいに往復する (両端で 1 秒止まる)。ボットは、領域 (廊下の外周ぞい) に鉄球が来ない隙 (0.9 秒) を待って渡る (`waitClear`)。**待つ点は、領域から 2m (止まらずに渡り切る距離) より離す** (1.8m だと、待たずに渡って被弾した)。**4 階の西の鉄球は、最初、最後の坂 (山頂へ) の足元と重なって (z −14)、球が坂にめり込み、坂をのぼる人が被弾した (批評 A 中・B 中) → z −8 に移し、「鉄球の通り道が箱に刺さらない」テストを足した** (回転した箱 = 坂も検査)。鉄球の待ち時間は、往復の周期との位相で 5 秒ほど変わる (人も同じ) → **バランスの測定 (allStages) は、鉄球のあるステージも、開始の位相をずらした 4 回の平均** (風・水位のステージと同じ)。
* **ボット**: `stage5RouteFor(stage, { gates, dirs, stars, slow })` が、塔の状態機械 (階 j の「着いた側 A」/「坂の側 R」) から組み立てる。坂の側 → 坂をのぼる / 着いた側 → ゲート (使える体) か、リングを半周 (向きは東西)。星は、通る廊下で拾うか、通らない廊下は往復。寄り道の星は、近道か (`slow` に入れると) だれでも行ける遅い道で。広場は、塔の南がわの道 (z = −68) を回る (最初は、広場の星 → 坂の足元へまっすぐ向かって、木箱の部屋の壁・塔の壁に突っかかった)。名前つきルート: **main** (近道なし・戦わずに取れる 5 個を遅い道で) / **std** (STANDARD の最速) / **strong** (POWER・HEAVY・EXTREME の最速) / **light** (SPEED・JUMP の最速)。
* **設計で決めたこと**: ① 近道 (ゲート) を、(a) 広場の北から 1 階へ (広場を半周歩く 230m が、1 階の半周 + 坂と同じで、利得なし) (b) 4 階から山頂へ (4 階の半周 56m が短く、ゲートの手間のほうが長い) の 2 つはやめた。② 星を、**体型ごとの寄り道** (風の柱・高い台・木箱の部屋) と、**通り道の廊下の星**に分けた。③ 最初は、2 つの庭 (広場の東西 66m 先) だったが、寄り道が遠すぎて (+25 秒) 星が選ばれなかったので、広場の庭は 1 つ (南東 58m) にして、もう 1 つの敵の星を 4 階の西の廊下に移した。**設計は、まず解析のモデル (`scratch/s5/dp.py`: 階ごとの半周・坂・ゲートの時間と、体型ごとの速さ・できること) で、ゲートの種類と配置の組み合わせを数十通り比べてから、ボットで測った** (ゲートを全員が使える組み合わせは、足の速さだけで順位が決まり (SPEED 13 秒 〜 EXTREME 24 秒)、ゲートが少なすぎると半周の長さで決まる)。
* **バランス** (`tests/balance/allStages.test.ts`、最速の道。鉄球の位相 4 回の平均): SPEED 86・STANDARD 90・POWER 106・JUMP 112・HEAVY 120・EXTREME 128 秒 (S5 のリーダーは SPEED。STANDARD は 5% 差 = STAGE 4 の SPEED の 20% 差より小さい)。parTime 140 秒 (STANDARD の最速の約 1.6 倍。S ランクは 0.8 倍の 112 秒以下 = SPEED・STANDARD (JUMP は 112.4 秒でわずかに A)、A は 140 秒以下 = EXTREME まで)。星の組み合わせ 56 通り × 近道の使い方の測定 (ボット 1 回): 最速の 5% 以内の組み合わせは STANDARD 4・SPEED 2・JUMP 4・HEAVY 7・POWER 3・EXTREME 4。高い台は、直接跳べる SPEED・JUMP では常に最速に入り (−11〜−15 秒)、ほかのビルドには遠い寄り道 (+22〜+40 秒) になる。木箱の部屋は、壊せるビルドには安い (−11〜−15 秒)。広場の東の庭・3 階の東は +1〜+14 秒。
* **登れない壁のテスト**: 全階の壁 (6m) を、5 つの位置 × 4 つの辺で、ジャンプを 3 フレームおきに押しながら壁へ向かって歩く (全ビルド + jump 222 の体 (大きさ 1.0 / 1.6))。坂のとなり・ゲートの前だけは、本来の登り口として除く (jump 222・大きさ 1.6 は、3 階の坂のとなり (坂の途中 2m から 6m の壁の上へ跳び乗る) で壁の上に着く。坂を短くするだけで、害は小さい)。高い台の屋根のテストは、台の上から東へ助走して跳ぶ (jump 222 の大きさ 1.0 / 1.6 / 0.6・jump 150・speed 222 を含む)。
* **ミニマップ**: ステージ定義の `minimapHeightShade` が true (STAGE 5) だと、箱の足あとを、高いほど明るく、低い箱から先に描く (階の高さが分かる)。坂 (回転した箱) は、明るい黄色で道として描く。他のステージは変わらない (最初は、高さ 15m 超の箱がある (STAGE 3 の外壁など) ステージ全部に効いて、STAGE 3 の見た目が意図せず変わった = 批評 B 中 5)。
* **STAGE 5 の保存したベスト**: レジストリの版 `rev` = 3 (直線コースだった頃・批評の前の v0.15.0 のベストは、起動時に捨てる)。

## 6. ランキング方針 (PHASE 13 で詳細化)

* バックエンド: Firebase Firestore (Spark 無料枠) + 匿名認証。**REST 直叩き**で SDK を同梱しない。API キーは公開前提の識別子で秘密ではない。管理者権限/秘密鍵はクライアントに置かない。
* 1 ユーザー 1 ドキュメント (uid)。ルールで「ベストの更新のみ」「値域」「スプリット合計 = 総タイム」「最小可能タイム」を検証。
* 記録: timeMs / splits[5] / level / characterSummary / stats / paramsHash / gameVersion / flags / 実時間と シム時間の差。後から検証ロジックを追加できるよう `schemaVersion` を持つ。
* 完全な不正防止は目標外。異常値検出とフラグ化まで。
* 未設定/オフライン時はランキング機能のみ「利用不可」表示、ゲーム本体は影響を受けない。
